# 信任与低信任审查

在 Paperclip 公司中，部分工作源于您无法担保的输入：不受信任的拉取请求（pull request）、外部工单、依赖项差异，或智能体基于上述任何内容生成的输出。信任预设的目标很简单——在运行期间将此类工作*隔离*，并确保其产出在经过人类或可信审阅者检查之前，不会被静默输入到更高信任级别的智能体中。

本页介绍 Paperclip 提供的两种信任预设，当智能体或其工作被视为低信任时实际发生了什么变化，智能体如何在不完全突破边界的情况下向父级问题报告进度，以及隔离的工作在被视为接受之前如何被审查和提升。

建议先阅读 [执行策略](../guides/power/execution-policy.md)——信任预设叠加在相同的执行策略机制之上，低信任运行依赖于其中描述的隔离工作区和沙箱机制。

> **这是隔离，而非隐私。** Paperclip 公司中的标准工作默认保持公司可见——Paperclip 控制台用户和公司内行动者仍可检查公司工作对象。低信任隔离范围更窄：它限制低信任智能体通过 Paperclip API 可以读取或更改的内容，并阻止原始不受信任的输出被自动提升到更高信任级别的智能体上下文中。它不是一套通用的项目、问题或人类隐私系统。

---

## 两种预设

Paperclip 仅提供两个核心信任预设，因此隔离决策在所有地方强制执行——包括社区版，即使 UI 中不可用策略编辑功能。

- **`standard`** — 默认值。这是您熟悉的正常、公司可见的协作模型。常规智能体行为与以往完全一致，除非策略另有规定，否则每个智能体都获得此预设。
- **`low_trust_review`** — 一种针对可能消耗敌对或提示注入输入的自动化工作的可选隔离预设。对于不希望智能体的读写范围扩展到整个公司，且其输出应在审查前被隔离的任务类型，请启用此预设。

默认预设是 `standard`；`low_trust_review` 仅在策略明确选择加入时生效。

## 为 GitHub 机器人选择智能体

对于可能包含来自公司外部指令的拉取请求和对话，请使用专用的低信任审查智能体。私有仓库仍可能包含不受信任的代码、评论、依赖项和生成内容。

在连接智能体之前：

1. 打开智能体的配置，并在其信任设置中选择 **低信任审查**。
2. 设置覆盖审查任务的工作边界，例如它们的专用项目。没有具体范围的预设无法运行。
3. 在运行时设置中配置隔离工作区和活动的沙箱环境。低信任 API 权限不会为宿主本地进程提供沙箱保护。
4. 仅允许工作所需的工具能力。将提供商凭证保留在受治理的连接中，而不是嵌入到提示或仓库文件中。

机器人连接的调用者权限及其智能体的信任预设保护的是不同的边界。为外部 GitHub 用户提供受限的访客配置文件，不能替代配置智能体的信任预设和运行时。负责任的发起者不会把自己的个人凭证交给访客。

设置警告不会更改所选智能体的权限。如果您继续使用标准智能体，请审查其现有的访问权限和运行时配置：当它读取外部内容时，其正常能力仍然重要。PR 内部的指令绝不能被视为扩展该访问权限的许可。

## 预设如何选定

低信任预设不是单一开关。Paperclip 通过读取您已用于执行的相同 JSON 策略，从最多四个来源解析有效预设：

| 来源 | 所在位置 |
|---|---|
| **智能体** | 智能体的 `permissions` — `trustPreset` 和 `authorizationPolicy.trustBoundary` |
| **项目** | 项目的 `executionWorkspacePolicy.authorizationPolicy` |
| **问题** | 问题的 `executionPolicy.authorizationPolicy` |
| **运行** | 运行的 `executionPolicy.authorizationPolicy` |

解析器将这些来源组合。如果*任何*来源要求低信任——无论是通过命名 `low_trust_review` 预设，还是携带 `trustBoundary`——该工作的有效预设即变为 `low_trust_review`。然后各来源的边界相交：**更窄者始终胜出**。您不能通过放宽某一层来拓宽边界；您只能使其更紧。

有两点使解析**失败关闭**（工作被拒绝而非以较弱的隔离运行）：

- 命名*不同*公司的策略来源，或使用不支持的预设值。
- 未解析为具体范围的低信任预设。低信任审查必须落在真实的、公司本地的目标上——根问题、一个或多个项目 ID，或明确的问题 ID 列表。如果这些都不存在，解析将被拒绝。

### 信任边界内部

当 `low_trust_review` 解析时，它产生一个单一的合并边界。这些是您可以设置在 `trustBoundary` 上的字段，全部限定在一个公司内：

- `mode` — 始终为 `low_trust_review`。
- `companyId` — 边界所属的公司。命名其他公司的边界将被直接拒绝。
- `projectIds` — 低信任工作可触及的项目。
- `rootIssueId` — 工作被限制的问题子树。
- `issueIds` — 明确的问题允许列表。
- `allowedAgentIds` — 边界内允许的智能体。
- `allowedSecretBindingIds` — 运行可引用的密钥绑定。
- `allowedToolClasses` — 运行允许使用的工具类。
- `outputPromotionTarget` — 提升输出允许落地的位置（一个问题）。

`rootIssueId`、`projectIds` 或 `issueIds` 中至少必须存在一个——解析器在允许低信任工作运行前要求的具体范围即为此。

## 运行时发生了什么变化

当运行解析为 `low_trust_review` 时，除非 Paperclip 能实际执行边界，否则拒绝启动。托管的低信任运行**失败关闭**，除非满足以下所有条件：

- **实例启用了隔离工作区。** 没有它们，就没有安全的地方来隔离工作。
- **执行工作区模式为 `isolated_workspace`。** 共享或宿主本地工作区对于低信任工作不可接受。
- **正在运行的问题位于解析后的边界内** — 要么被直接命名，要么在允许的项目中，要么是边界 `rootIssueId` 的后代（祖先检查限于有限深度）— 或者它是人员直接指示智能体执行的确切任务（参见 [人员直接要求的工作](#work-a-person-asks-for-directly)）。边界外的任何其他问题将被拒绝。
- **环境使用 `sandbox` 驱动程序。** 托管低信任执行不允许使用宿主本地适配器进程；您需要沙箱环境。

在此基础上，还适用两项进一步约束：

- **密钥受限。** 低信任运行只能引用其 ID 列在边界 `allowedSecretBindingIds` 中的密钥绑定，且内联敏感环境变量（原始 API 密钥、令牌等）将被拒绝——它们必须通过允许的绑定提供，而不是粘贴进去。
- **运行时服务默认拒绝。** 除非边界明确授予 `runtime.manage` 工具类，否则低信任运行不能启动或变更工作区运行时服务。如果尝试且该授权缺失，运行将被停止。

内置的低信任工具类在设计上是只读且保守的：`git.read`、`github.pr.read` 和 `tests.local`。这是该预设旨在处理的工作形态——读取不受信任的变更，运行本地测试，报告结果——而不是向外扩展并变更更广泛的公司内容。

**没有仓库？任务获得一个私有文件夹。** 当任务的项目未配置工作区且没有其他策略选择工作区策略时，低信任运行将在沙箱内仅为该公司和任务工作的私有目录中运行。它不需要 Git 仓库，其内容会在每轮执行之间以及任务重新分配后保留。它永远不会拉入共享项目目录或智能体自己的文件夹。如果您*已*配置了工作区或明确的 Git 策略，它仍必须可用——缺失或损坏的检出不会静默回退到空文件夹。

如果您一直使用本地 Docker 工作流手动进行不受信任 PR 的审查，这仍然适用于手动审查。但 Paperclip 作为托管低信任执行运行的任何内容都通过上述沙箱隔离路径。

## 低信任智能体仍可执行的操作

隔离针对的是外部输入，而非排斥运行智能体的人员。低信任智能体仍可执行几种类型的工作，每种都绑定到特定的、已记录的授权来源。

<a id="work-a-person-asks-for-directly"></a>
### 人员直接要求的工作

您可以在自己的智能体聊天中与低信任智能体对话，或分配给它一个位于其正常边界之外的任务。Paperclip 将此视为您（人员）的指示，并允许智能体处理它。

例外情况故意保持狭窄：

- **它来自真实记录。** Paperclip 使用您的聊天对话，或您在分配任务时记录在运行唤醒请求上的已登录人员。无需填写单独的权限，客户端也不能声称是您。
- **仅已登录的看板用户有效。** 智能体的负责用户、由外部连接器归因的发送者、代表用户操作的插件，或来自其他智能体的声明均不符合条件。
- **它涵盖一个任务。** 智能体可以读取、评论和更新该确切任务。它不扩展到其他任务、子任务、整个项目、配置、指令、密钥或运行时管理。正常的负责用户检查仍然适用。
- **重新分配会取消它。** 当任务易手时，早期的人员请求被取消，重新分配回去不会恢复它们。同一任务的自动重试会传递该指示；被取消的运行不能授权重试。
- **沙箱规则不放宽。** 运行仍需要沙箱驱动程序和隔离工作区，且该例外永远不会写入智能体继承的边界中。

如果您将任务分配到 **Backlog（待办池）**，该分配会被记住，以便稍后的启动获得授权，而不会提前开始工作。

### 在边界内创建任务

低信任并不阻止智能体组织自己的工作。只要它们留在其项目或根任务范围内，它可以创建分配给自己的任务，以及其自身任务的子任务：

- 创建任务通过正常的分配权限检查——包括任何分配限制和负责用户的权限——即使新任务未分配。
- 仅当边界明确允许该智能体时，分配给其他智能体才有效。分配给Paperclip 控制台用户将被拒绝。
- 新任务保留创建者的隔离状态及其隔离的来源归因。
- 精确的 `issueIds` 允许列表不会自动覆盖新的子任务，且被允许的父任务不会开放无关的项目。`rootIssueId` 范围包括其后代。

<a id="instruction-edits-from-your-own-chat"></a>
### 来自您自己聊天的指令编辑

通常低信任智能体不能更改自己的指令。有一个例外：当您在**您自己的**与该智能体的智能体聊天中要求它更新其指令时，它可以保存自己的 `AGENTS.md` — 即使在 `low_trust_review` 下。

使其足够安全的原因：

- **聊天轮次即权限。** 它需要智能体的当前身份以及您在该聊天中记录的、已登录的消息。任务上的您的名字、来自连接器或插件的消息、普通任务或子任务，或来自其他用户的消息均不符合条件。您之前的消息不能授权后来的外部请求，且智能体在聊天期间读取的内容不是来自您的请求。
- **每次保存时检查您当前的权限。** 如果您不能编辑该智能体的指令，保存将失败——包括在成功、失败或超时的运行后收集智能体私有文件夹时。取消运行、重置聊天、重新分配、删除消息或失去访问权限都会终止该例外。
- **它保持小型。** 它仅涵盖智能体自己的指令。它不允许智能体编辑其他智能体的指令、更改通用配置或访问其他特权 API，且永远不会写入智能体的信任策略。

一个诚实的警告：Paperclip 检查*谁*发送了消息，而非其含义，且不要求您批准每次编辑。如果智能体在您的聊天期间读取到敌对内容，提示注入仍可能发生，因此请留意它更改的内容。

当保存被拒绝时，智能体应告诉您哪个操作被阻止及原因——例如，当前运行不是您的直接聊天，或您没有编辑权限。然后您可以在自己的聊天中请求，或在 [指令选项卡](../guides/org/agents.md#instructions-tab) 上自行进行编辑。创建另一个任务不能授权该变更。

## 向父级问题报告

大多数实际工作被拆分为父级问题和子级。处理子级的智能体通常需要告诉父级进展如何——“找到原因，仍在挖掘”或“这被阻塞在您需要做出的决定上”。该报告必须从一个问题跨越到另一个问题，这正是信任边界所怀疑的那种移动。因此 Paperclip 为其授予一个狭窄的、可审计的跳跃，仅此而已。

### 标准运行可评论其直接父级

在 `standard` 预设下，智能体可以在其当前检出的问题的直接父级上发布评论——即使该父级分配给不同的智能体。此前，该评论作为任意跨问题写入被拒绝，这可能静默地停滞父级/子级协调。现在，该请求被允许，决策原因为 `allow_direct_parent_report`。

对于该授权适用，以下每一项都必须为真：

- 操作是评论（`issue:comment`）— 其他任何操作均不符合条件。
- 智能体通过运行进行操作，且该运行属于同一智能体和同一公司。
- 运行的上下文命名了智能体正在处理的问题。
- 该问题分配给操作智能体（`assigneeAgentId`）。
- 该问题确实**被此运行检出**（`checkoutRunId`）— 仅被分配是不够的。
- 目标问题是该问题的直接 `parentId`。
- 有效预设解析为 `standard`。

成功的授权会被审计。`issue.comment_added` 活动条目携带 `directParentReportGrant: true`，因此您稍后可以区分哪些评论是通过此授权跨越问题边界的，而非通过普通访问。

### 界限所在

一次跳跃，仅限评论。其他一切仍被拒绝：

- **祖级及更高层级。** 此处不遍历祖先——仅计算直接的 `parentId`。目标为祖父级任务的评论将被拒绝。
- **同级**，包括同一父级的其他子级。
- **更改父级问题。** 针对父级的 `issue:mutate` 请求——例如状态变更——仍被拒绝。
- **在父级上写入文档。**
- **重新打开或恢复已关闭的父级。** 如果父级已关闭，评论本身被接受，但该请求上的任何 `reopen` 或 `resume` 意图被丢弃，且父级状态保持原样。即使已关闭的父级未分配，甚至恰好分配给报告智能体，此规则也成立——在所有情况下，授权仅限评论。这与基于提及的授权已获得的仅限评论处理相同。

### 隔离子级通过净化中继报告

`low_trust_review` 运行**不**获得此授权。来自低信任运行的直接父级评论被拒绝，因为允许其通过会将不受信任的文本直接带入更高信任父级的上下文——这正是隔离旨在防止的。唯一的例外是现有的提及路径：如果父级上的受信任评论提及了低信任智能体，该提及授权仍然适用（`allow_issue_mention_grant`），且评论落地。

这会导致当隔离子级放弃时，父级永远等待，因此 Paperclip 中继*事实*而不中继文本。当有效预设不是 `standard` 的问题移动到 `blocked` 或 `cancelled` 且它有父级时，Paperclip 在直接父级上写入一条由 `system` 撰写的简短评论：指向子级的链接及其移动到的状态。不复制子级产生的任何内容——不是其评论正文，不是其输出。如果父级有智能体受让人且未关闭，该智能体被唤醒，以便有人实际接手停滞。

两个值得了解的细节：

- **仅 `blocked` 和 `cancelled` 中继。** 其他转换不中继——这是停止信号，而非进度更新。
- **中继是幂等的。** 每个子级每个停止状态一次中继，因此频繁在 `blocked` 中进出的问题不会向父级发送垃圾信息。每次中继记录为 `issue.comment_added`，带有 `source: "child_stop_relay"`。

这遵循与下文提升相同的原则：父级得知某事停止了，而受信任的审查者仍必须打开隔离的输出以了解*原因*。

## 审查和提升低信任输出

运行时的隔离只是故事的一半。另一半是低信任智能体写入的内容发生了什么。

当低信任智能体创建问题、评论、文档或工作产品时，Paperclip 为该工件标记**来源信任元数据**，并赋予其处置状态 `quarantined`。隔离的工件被存储，但其原始正文被保留在更高信任智能体上下文之外。在更高信任智能体通常会读取正文的地方，它反而看到一个占位符，解释隔离的低信任输出被省略，且受信任的审查者可以检查并提升净化版本。评论呈现和元数据随正文一起被剥离，因此原始工件中的任何内容都不会意外泄漏到受信任运行中。

来源信任记录携带足够的溯源信息以稍后审计工作：

- `preset` — 产生该工件的信任预设。
- `disposition` — `quarantined` 或 `promoted`。
- `sourceIssueId`、`sourceRunId`、`sourceAgentId` — 工件的来源。
- `promotedFrom` — 提升所基于的原始工件，包括其 `artifactKind`（`issue`、`comment`、`document` 或 `work_product`）、`artifactId` 和 `issueId`。
- `promotedByActorType`（`agent`、`user` 或 `system`）、`promotedByActorId` 和 `promotedAt` — 谁提升了它以及何时。

**提升**是将隔离输出转变为受信任智能体可操作之物的刻意、经审查步骤。受信任的审查者检查隔离工件，并写入带有处置状态 `promoted` 和指向原始的 `promotedFrom` 链接的净化版本。只有那时，内容才流入更高信任上下文。没有自动提升——原始不受信任的输出永远不会被静默升级。

此来源信任标签位于工件本身：问题、问题评论、文档和问题工作产品各自携带它，因此隔离和提升状态随工作在其被读取的任何地方移动。

## 何时使用低信任审查

当智能体的任务是处理您不控制的输入，且您希望硬性保证其范围和输出保持隔离时，请使用 `low_trust_review`：

- 审查不受信任或外部的拉取请求。
- 分诊来自公司外部提交的工单或报告。
- 检查依赖项差异或第三方变更。
- 对可能携带提示注入负载的任何内容运行智能体。

对于其他所有情况，`standard` 是正确的默认值——它保持正常协作快速且公司可见，这是大多数工作所需要的。
