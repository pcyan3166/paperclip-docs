# 密钥作用域与责任用户

在 Paperclip 中，一个密钥由两部分组成：定义（名称及其适用范围）和存储在其下的值。定义的“作用域”决定了由谁提供该值。公司级密钥携带一个值，供公司内的所有运行任务使用。用户级密钥为每个自然人保留一个独立的值，运行任务会解析属于该运行任务责任人的那个值。在运行任务分发之前，Paperclip 会检查责任人是否已提供该运行任务所需的所有用户级值；如果缺少任何一个，运行任务将不会启动。

## 为什么存在作用域

团队成员不共享凭证。如果每个密钥只有一个全公司通用的值，那么当第二个人加入时，必然会发生以下两种情况之一：他们的运行任务借用他人的密钥，或者他们根本无法运行智能体。借用密钥的危害比表面看起来更严重。在他人凭证下执行的工作无法归因于实际发起请求的自然人，且提供商侧的按人限流或审计追踪将不再准确。

按用户区分的值消除了这种分叉。每个自然人为同一个定义提供自己的值，运行任务在背后发起者的凭证下执行，添加新团队成员意味着无需传递密钥。这正是该功能存在的原因：它是安全的多用户和云端执行的前提条件，在这种场景下，多个自然人在同一家公司内驱动智能体，且他们之间不应无法区分。

## 一个心智模型

公司级密钥就像挂在墙钩上的一把钥匙。任何运行任务都可以取用，且所有运行任务使用同一把钥匙。用户级密钥则像一张徽章：每个人携带自己的徽章，运行任务展示的是其所服务自然人的徽章。智能体本身没有徽章；无论有多少个智能体接触某个任务，所展示的徽章始终属于某个自然人。

绑定决定了哪些“门”需要出示徽章：绑定到目标（如环境、智能体、项目等）的定义声明了该处的运行任务需要此密钥。分发检查就像一道旋转门。它在运行任务进入之前读取徽章，而不是在运行任务进行到一半时读取，并且对于相同的徽章，它始终给出相同的答案：要么责任人已提供该值，要么没有。

## 运行任务如何解析密钥

从定义开始。创建密钥意味着预先声明其作用域——在作用域选择器中，这些选项显示为 **Company**（公司），表示一个共享值；或 **Each user**（每个用户），表示每个自然人一个值。作用域是定义的一个属性，因此无论哪种情况，公司内的每个人看到的定义都是相同的；区别在于预期由谁来填充该值。

![密钥界面中的用户级密钥定义，其中用户作用域与公司作用域区分开来](../../user-guides/screenshots/light/secrets/user-secret-definition.png)

在用户作用域下，每个人在产品的 Company Settings → Secrets → My secrets（公司设置 → 密钥 → 我的密钥）路径下存储自己对该定义的值。你的值仅属于你：当你是某个运行任务的责任人时，该值会被使用，且永远不会向任何人（包括管理员）回显。

![“我的密钥”选项卡，当前用户在此为用户级定义提供自己的值](../../user-guides/screenshots/light/secrets/per-user-value-entry.png)

定义绑定到需要它们的对象——环境、智能体、项目及其他目标——这就是运行任务最初需要密钥的原因：运行任务继承其运行目标所绑定的定义，这些定义就是它必须提供的密钥。

最后一个要素是归属。每个运行任务都有一个责任人，即背后的自然人，密钥查找正是针对该身份进行解析。当分发评估一个运行任务时，公司级需求解析为共享值，而用户级需求解析为责任人已存储的值。运行任务是此处的常规路径，但并非唯一路径——有关少数没有运行任务支撑却能解析用户级密钥的操作，请参阅 [你自行执行的操作](#actions-you-take-yourself)。

检查本身是确定性的，且发生在分发之前。如果责任人已提供运行任务所需的所有用户级值，运行任务将继续执行，这些值会在运行时像其他密钥一样被注入。如果缺少任何值，运行任务将不会启动。

检查还会尽早暴露问题。创建一个其运行任务将需要尚未提供的用户级值的任务时，系统会在创建时警告你，并内联提示设置该值，而不是等到分发时阻止运行任务。

![在任务创建时暴露的检查：责任人尚未提供的用户密钥，并带有设置值的内联提示](../../user-guides/screenshots/light/secrets/dispatch-check.png)

检查确认的是存在性，而非正确性。它保证责任人已提供一个值；如果该值错误或已过期，仍会在实际使用处失败。你所获得的是消除了一类特定的故障：运行任务启动、执行工作，然后因为从未存储所需凭证而在中途死亡。

## 你自行执行的操作

并非每次使用密钥都涉及运行任务。产品中有几项操作在你点击的瞬间就会访问密钥，不涉及运行任务，也不涉及分发检查：在设置智能体时测试适配器的环境，以及从设置中登录智能体到 Claude。

对于这些操作，你就是责任人。Paperclip 从请求本身推断出这一点——即已登录的用户，或者当请求携带智能体令牌到达时，智能体所代表的用户。请求体永远无法指定责任人，因此所展示的徽章始终是你实际携带的那一个。

如果 Paperclip 无法确定你是谁，且配置需要一个标记为必需的用户级值，该操作将以 `responsible_user_missing` 停止。这与分发对责任人未提供值的运行任务给出的“失败关闭”答案相同：不会在回退身份上继续执行。

测试尚未保存的配置是一个有趣的案例。通常，用户级值必须绑定到请求它的对象，这种绑定说明了该定义属于该智能体配置中的此密钥。你正在填写的配置没有绑定，因为它尚未保存。因此，对于该操作，Paperclip 直接从定义解析你自己的值，仅检查该值是否属于你。你的团队成员的值无法被触及，测试要么在你的凭证下运行，要么根本不运行。

已保存的智能体保持更严格的路径。将已保存的智能体登录到 Claude 时，会针对为该智能体记录的绑定进行解析，因此从未绑定到那里的必需用户级引用会以 `binding_missing` 被拒绝，而不是静默解析。在这两种情况下，公司级引用以相同方式解析。

## 查看谁访问了密钥

每次运行时解析都会留下一个脱敏条目，你可以阅读它们。打开 Company Settings → Secrets（公司设置 → 密钥），选择一个公司密钥，然后切换到 **Access events**（访问事件）选项卡。条目会记录发起请求的消费者、结果，以及——当涉及用户时——责任人，如果凭证所有者是其他人，还会记录凭证所有者。

消费者被如实记录，而不是四舍五入到最近的智能体。测试环境会记录你选择的环境，或者当你未选择时，记录为 `system` 消费者下的 `adapter_test`，因此环境探测不会在日志中看起来像是由智能体执行的。

列出或同步智能体的技能会将智能体记录为消费者，并将你记录为背后的操作者。这两个操作故意完全跳过用户级密钥，因此它们对日志的贡献仅限于对智能体配置中已引用的公司密钥的归属记录——而不是对按用户区分的值的任何新访问。

打开一个用户级定义，其 **Access events**（访问事件）选项卡不会列出条目：用户级密钥的访问事件是在运行时解析发生时，记录在每个成员自己存储的值上，而不是记录在共享定义上。

## 选择作用域

作用域遵循凭证的所有权。属于共享基础设施的密钥，例如整个团队读取的数据库，适合公司作用域：只有一个真实值，按用户拆分只会增加无谓的工作。颁发给个人的密钥，例如外部服务的个人 API 密钥，适合用户作用域：每个自然人已经拥有自己的密钥，重点在于运行任务使用正确的那一个。

这种权衡是真实的。用户作用域为每个自然人增加了一个入职步骤：新团队成员的运行任务在分发时会被挂起，直到他们提供自己的值，而公司级密钥本可以让这些运行任务立即启动。这种成本是有意为之的，因为一个在启动前被挂起且原因清晰的运行任务，比一个中途失败或静默在他人凭证下执行的运行任务成本更低。但这意味着用户作用域不应成为反射性的默认选择；对于真正共享的凭证，公司作用域更能描述现实。

## 在密钥模型中的位置

作用域回答的问题与密钥模型的其余部分不同。提供商和保险库（在 [密钥参考](../../reference/deploy/secrets.md) 中介绍）决定密钥材料存储在哪里以及 Paperclip 如何访问外部存储。作用域决定谁提供值以及哪些运行任务可以使用它。如果你是密钥的新手，先阅读那一页会有帮助；本页假设你已了解基础知识，仅解释作用域层。

命名是第三个独立的问题。密钥名称中的斜杠为密钥屏幕提供了一个文件夹树供浏览，这种分组与作用域无关——一个文件夹可以愉快地同时包含公司级和用户级密钥。有关如何推导该树以及如何将密钥归档到其中，请参阅 [密钥文件夹](./secret-folders.md)。
