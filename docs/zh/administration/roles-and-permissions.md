# 角色与权限

这是关于公司内人类访问权限如何决定的参考文档。如果您想要“成员”页面的逐步操作指南，请参见[公司管理](./company.md)；本页是其背后的查找表——包含每个角色、每个权限键，以及 Paperclip 用于组合它们的规则。

两层结构相互叠加：

- **成员角色** — 一个公司范围的标签（`Owner`、`Admin`、`Operator`、`Viewer`），携带一组*隐式*授权。
- **显式授权** — 在角色已赋予的权限之上，您在成员上勾选的单独权限键。

还有一个层级位于公司*之上*：**实例管理员**，将在文末介绍。

> **注意：** 人类和智能体通过*相同*的权限引擎运行——无论主体是人还是智能体，授权都是针对 `(company, principal type, principal id, permission key)` 进行解析的。本页描述的是人类侧。智能体报告树（CEO、经理、下属）是一个独立的概念；请参见[组织结构](../guides/org/org-structure.md)。

<a id="the-four-company-roles"></a>
## 四种公司角色

| 角色 | 适用对象 | 隐式授权 |
|---|---|---|
| **所有者 (Owner)** | 运营公司的人员 | `agents:create`、`agents:configure`、`skills:create`、`environments:manage`、`users:invite`、`users:manage_permissions`、`tasks:assign`、`joins:approve`、`tools:manage_connections`、`tools:manage_runtime`、`tools:use`、`tools:admin` |
| **管理员 (Admin)** | 负责接入人员和智能体的受信任操作员 | `agents:create`、`agents:configure`、`skills:create`、`environments:manage`、`users:invite`、`tasks:assign`、`joins:approve`、`tools:manage_connections`、`tools:manage_runtime`、`tools:use`、`tools:admin` |
| **操作员 (Operator)** | 日常编辑公司工作的动手成员——新邀请的默认角色 | `agents:create`、`agents:configure`、`skills:create`、`environments:manage`、`users:invite`、`tasks:assign`、`pipelines:write`、`tools:manage_connections`、`tools:manage_profiles`、`tools:manage_runtime`、`tools:use`、`tools:admin`、`tools:view_audit`、`audit:view_agent_actions` |
| **查看者 (Viewer)** | 只读观察者 | *(无)* |

**所有者**与**管理员**之间的唯一区别是 `users:manage_permissions`——管理员可以邀请人员并批准他们，但不能更改其他成员的角色或授权。这是专门保留给所有者的权限。

**操作员**是日常编辑角色，也是邀请时默认分配的角色（除非您选择其他角色）。操作员可以雇佣和配置智能体、编辑技能和环境、邀请人员、分配工作、编写流水线、连接账户并管理工具，以及读取两个审计轨迹。他们*不能*做的是批准加入请求（`joins:approve`）或更改任何人的角色或授权（`users:manage_permissions`）——这两项权限保留给管理员和所有者。

这一界限也适用于邀请，因此邀请不能授予创建者所不具备的成员权限（如批准加入或管理权限）。操作员可以邀请新的操作员和查看者。邀请某人成为**管理员**还需要 `joins:approve`，而邀请**所有者**则需要同时具备 `joins:approve` 和 `users:manage_permissions`。

有两个怪癖值得了解：

- **操作员捆绑包包含四个所有者和管理员捆绑包中没有的键：** `pipelines:write`、`tools:manage_profiles`、`tools:view_audit` 和 `audit:view_agent_actions`。如果您希望所有者或管理员编写流水线或读取审计源，请将这些键作为显式授权授予他们。
- **现有操作员在重启时补齐权限。** 当 Paperclip 服务器启动时，它会添加成员缺失的任何角色默认值。在捆绑包扩大之前加入的操作员会在当时获得新键，而他们已持有的授权保持其范围不变。

第五个选项，**未设置 (Unset)**，出现在角色下拉菜单中。它使成员没有任何隐式授权——当您希望仅通过显式授权手动挑选权限而不包含其他内容时，这很有用。（在底层，旧值 `member` 被视为 `operator`。）

<a id="the-permission-keys"></a>
## 权限键

共有二十一个权限键。其中十六个作为默认值出现在一个或多个角色中；五个是**仅限显式授权**——没有角色包含它们，因此成员只能通过显式授权获得它们。

| 权限键 | 允许的操作 | 默认所属角色 |
|---|---|---|
| `agents:create` | 在公司中创建（雇佣）新智能体 | 所有者、管理员、操作员 |
| `agents:configure` | 更改现有智能体的设置——其适配器配置、指令、角色和预算 | 所有者、管理员、操作员 |
| `agents:suggest-changes` | 提出对智能体设置的更改以供审查，而不直接应用 | —（仅限显式） |
| `skills:create` | 创建和管理公司技能 | 所有者、管理员、操作员 |
| `skills:suggest-changes` | 提出对公司技能的更改以供审查，而不直接应用 | —（仅限显式） |
| `environments:manage` | 创建、编辑和移除智能体运行的执行环境 | 所有者、管理员、操作员 |
| `tools:admin` | 设置公司共享的工具管道——工具应用背后的 stdio 命令模板，以及智能体通过连接的 MCP 网关（包括签发和撤销网关令牌） | 所有者、管理员、操作员 |
| `tools:manage_connections` | 选择工具连接安装在哪些智能体和项目上 | 所有者、管理员、操作员 |
| `tools:manage_profiles` | 保留用于工具配置文件管理。目前可授予，但尚无功能检查它——见下方说明 | 操作员 |
| `tools:view_audit` | 读取网关的工具调用审计轨迹 | 操作员 |
| `audit:view_agent_actions` | 打开公司的**审计**源——智能体行为的记录——并将其下载为 CSV | 操作员 |
| `tools:use` | 从面板尝试连接的测试调用界面 | 所有者、管理员、操作员 |
| `tools:manage_runtime` | 检查正在运行的工具运行时插槽，并停止或重启它们 | 所有者、管理员、操作员 |
| `inbox:manage` | 操作*另一个*人的收件箱。智能体处理其负责用户的收件箱不需要此键——见下方说明 | —（仅限显式） |
| `users:invite` | 创建和撤销公司邀请链接 | 所有者、管理员、操作员 |
| `users:manage_permissions` | 查看和更改成员的角色和授权 | 所有者 |
| `tasks:assign` | 将任何问题分配给公司中的任何智能体或成员 | 所有者、管理员、操作员 |
| `tasks:assign_scope` | 分配问题，但仅限于受限范围（例如，单个经理的子树）。这是当主体**不**持有广泛的 `tasks:assign` 授权时，Paperclip 检查的*范围回退* | —（仅限显式） |
| `tasks:manage_active_checkouts` | 重新分配或清除当前由其他受让人签出的问题——用于解除工作卡住的覆盖权限 | —（仅限显式） |
| `pipelines:write` | 创建和修改流水线自动化 | 操作员 |
| `joins:approve` | 批准或拒绝人类和智能体的加入请求 | 所有者、管理员 |

### 关于直接操作与建议操作的对子

两个键成对出现——一个*直接*键立即应用更改，一个*建议*键仅提出更改以供审查：

- **`agents:configure`** 允许成员直接更改现有智能体。**`agents:suggest-changes`** 是较柔和的对应项：持有此键（但不持有 `agents:configure`）的成员可以*提出*对智能体指令或配置的更改，该更改在生效前需经过审查。这是驱动内置[反思教练](../reference/api/built-in-agents.md#the-reflection-coach)等辅导流程的功能——它可以建议改进智能体的 `AGENTS.md`，而无需热替换。
- **`skills:create`** 允许成员直接编写和编辑公司技能。**`skills:suggest-changes`** 允许成员提出对公司技能的编辑以供审查，而不是直接写入。

### 关于仅限显式的键

五个键从未出现在角色的默认值中，因此成员只能通过显式授权获得它们——来自成员编辑器，或 CLI 上的 `member role-and-grants`：

- **`agents:suggest-changes`** 和 **`skills:suggest-changes`** — 上述描述的审查门控建议键。将它们授予您希望提出改进建议但不具备直接写入权限的成员（或智能体）。
- **`tasks:assign_scope`** 是允许某人在*其职责范围内*进行委托，而不赋予其公司范围的分配权限的方式。当成员拥有 `tasks:assign_scope` 但不拥有 `tasks:assign` 时，Paperclip 会根据附加在授权上的范围评估该授权，仅当目标落在该范围内时才允许分配。在授权负载中设置范围（通过成员编辑器的授权，或 CLI 上的 `member role-and-grants`）。
- **`tasks:manage_active_checkouts`** 是一个逃生舱。通常，智能体已签出的问题对其他人在释放前是禁止访问的；此授权允许持有者重新分配或清除该活动签出——当智能体在任务中途停滞时非常有用。
- **`inbox:manage`** 管理*跨用户*收件箱访问。这对智能体最为重要：智能体可以在不持有此键的情况下操作其负责用户的收件箱，但一旦需要触及他人的收件箱，Paperclip 就会寻找 `inbox:manage` 授权——然后检查该授权的范围是否实际覆盖被操作的用户。将其授予您希望在其负责用户之外进行收件箱分诊的智能体，并设置好范围。

> **`inbox:manage` 与低信任预设。** 在低信任审查预设下运行的智能体默认被拒绝 `inbox:manage`，以及其他公司范围和特权操作。提高智能体的信任预设与授予该键是独立的决定——持有该授权的低信任智能体仍会被拒绝。

### 关于工具、审计和流水线键

这些键不再仅限显式，但它们在各角色中分布不均，因此放在一起看有助于理解：

- **六个 `tools:*` 键。** 操作员获得全部六个。所有者和管理员获得四个——`tools:manage_connections`（决定哪些智能体获得连接）、`tools:manage_runtime`（照看正在运行的工具进程）、`tools:use`（测试调用工具）和 `tools:admin`（连接应用和网关）——但不包括 `tools:view_audit`（在不触及设置的情况下读取网关的调用轨迹）或 `tools:manage_profiles`（保留且未检查——见下方说明）。查看者获得零个。注意 `tools:admin` 不是超集，因此持有它并不意味着拥有其他权限。请授予您实际需要的每个键。
- **`audit:view_agent_actions`** 是**操作员**捆绑包的一部分；其他人需要显式授权。它打开侧边栏中的**审计**页面——公司范围内智能体行为的源，以及单个智能体上对应的**审计**选项卡。它还涵盖该页面上的**导出 CSV** 按钮。如果没有该授权，页面仍会加载，但显示权限通知而非源，因此您可以将其授予审计员或合规审查员，而不赋予他们其他权限。有两个例外绕过检查：实例管理员，以及在本地信任模式下运行的面板。在授予之前值得了解这一点——导出本身记录在日志中，包括谁执行了导出、使用了哪些过滤器以及多少行数据离开了系统。此键与 `tools:view_audit` 不同：后者涵盖工具网关的调用轨迹，而此键涵盖公司范围内的智能体操作。
- **`pipelines:write`** 允许成员创建和编辑流水线自动化。它是**操作员**捆绑包的一部分；所有者和管理员需要显式授权。

> **`tools:manage_profiles` 尚未接线。** 该键存在且可以授予，但在此版本中没有端点检查它。今天编辑工具配置文件只需要一个具有除查看者外任何角色的活跃成员身份。将该键视为保留：授予它不会改变任何事，扣留它也不会阻止任何事。

<a id="how-grants-combine-precedence"></a>
## 授权如何组合（优先级）

规则简单且是累加的：

1. 从成员的**角色**隐式授权开始。
2. **添加**成员上勾选的每个显式授权。

没有“拒绝”层——显式授权永远只是*添加*能力，并且独立于角色存储。值得记住的实际后果是：

> 显式授权**在角色更改后持久存在。** 如果您将查看者提升为操作员，后来又将其降级回查看者，您手动勾选的任何框仍然保持勾选状态。更改角色仅交换隐式捆绑包；它永远不会清除显式授权。要完全剥离成员权限，请取消勾选其显式授权*并*适当设置角色（或**未设置**）。

## 智能体如何跨问题写入

上述权限键是模型的人类侧。智能体通过相同引擎运行，但问题*写入*通道——评论、更改字段、创建子问题和分配工作——遵循一条额外的规则，在推理智能体能够触及什么时，您应该理解这一点。

对于标准信任智能体，这四个通道在**智能体已能读取的任何问题上默认开放**。没有针对“在此问题上评论”或“重新分配那个问题”的单独每通道授权：可见性是它们共享的唯一门控，因此如果智能体可以读取问题，它就可以影响它；如果它不能读取问题，则所有四个通道都关闭。这取代了旧有的拼凑方案，其中每个通道都有自己狭窄的所有权、父级或提及规则。

有两个界限叠加在默认开放规则之上，并始终强制执行：

- **负责用户限定每次写入。** 智能体*代表*真实用户操作，只有当该负责用户本身被授权时，写入才会落地。智能体永远不会获得超出其负责用户权限范围的访问权限。
- **公司隔离、信任和运行锁仍然适用。** 跨公司写入在公司边界处被拒绝。低信任审查预设下的智能体、在其信任范围外操作的智能体，以及锁定到另一个进行中运行的问题，仍然被阻止——可见性打开门，但不移除其他墙壁。

当写入*被拒绝*时，拒绝会被写入以解释自身：它指出触发的界限、谁可以代替操作，以及合规的前进路径，以便被阻止的智能体可以绕过墙壁（例如，为正确的受让人创建子问题），而不是在模糊的拒绝上停滞。

### 每次运行的跨问题上限

为了防止单个失控的智能体运行在整个面板上引发级联写入，每个心跳运行最多可进行 **20 次跨问题写入**——评论和字段更新合计——针对*除*其唤醒问题之外的其他问题（`CROSS_ISSUE_INFLUENCE_LIMIT`）。计数按写入次数而非问题数量计算：无论是向同一问题写入 20 次，还是向 20 个不同问题各写入 1 次，都会达到上限。目前上限以**仅记录**模式运行——每个跨问题写入都被观察和记录，但没有被拒绝。硬性**执行始于 2026-08-11**（`CROSS_ISSUE_INFLUENCE_ENFORCE_AT`）；从该日期起，运行的第 21 次跨问题写入将被拒绝。评论记录将负责用户与操作智能体分开存储，因此无论哪个智能体执行了输入，问责轨迹都保持完整。

您可以从公司**审计**源中审查智能体实际执行的操作——包括这些跨问题写入和每个字段更改的前后状态——这需要上述描述的 `audit:view_agent_actions` 授权。

<a id="instance-admin-the-layer-above-companies"></a>
## 实例管理员——公司之上的层级

上述所有内容都是公司范围的。有一个角色位于任何单个公司之外：**实例管理员**（`instance_admin`）。

实例管理员可以：

- 触及并管理实例上的**每个**公司，包括其不是成员的公司；
- 提升和降级其他实例管理员；
- 管理每个用户可以访问哪些公司（`admin user company-access`）。

实例管理员权限从实例访问页面或 CLI（`paperclipai admin user promote <user-id>`）授予，而非从公司角色下拉菜单。它独立于公司角色——一个人可以是实例管理员，同时不是特定公司的成员，在这种情况下，访问页面会显示一个横幅，注明无成员身份的管理员级别访问。有关实例访问界面，请参见[设置](./settings.md#instance-access)，第一个实例管理员通过一次性的[面板认领](./cli-auth.md)流程建立。

### 云托管实例上的所有者实例管理员

如果您的实例由 Paperclip Cloud 管理，您可能希望拥有堆栈的人能够在其专用实例上打开实例设置，而无需询问任何人。这就是**所有者实例管理员**的用途。

在云托管实例上，人们不像自托管操作员那样认领实例——他们从 Paperclip Cloud 侧到达，携带*堆栈角色*：`owner`、`admin`、`member` 或 `support`。单独来看，这些角色中的任何一个都不附带实例管理员权限；控制平面拥有身份，实例永远不会为他们写入实例管理员角色。

所有者实例管理员是唯一的例外。当此功能开启时，持有 `owner` 堆栈角色的人被视为其自身实例的实例管理员。`admin`、`member` 和 `support` 不是——它们保持公司范围，与之前完全相同。

关于提升行为，有两点值得理解：

- **不写入任何内容。** Paperclip 在每次请求时，在实例信任 Paperclip Cloud 提供的身份之处，新鲜计算提升。永远不会为其创建实例管理员角色行。关闭该功能，所有者在下一个请求中立即降回公司范围，无需清理。如果实例因某种原因无法读取其自身设置，它假设该功能关闭：安全的答案胜出。
- **陈旧的角色行不会随行——对于云到达者。** 当某人通过受信任的 Paperclip Cloud 路径到达时，授权服务故意跳过 `instance_user_roles` 查找，并且他们遗留的 `instance_admin` 行在身份验证时被清除。因此，手动插入的行不能悄悄重新提升云租户。但要注意范围的精确性：该排除跟随*操作者*，而非实例。在同一实例上通过普通会话或面板 API 密钥登录的用户仍按常规方式针对 `instance_user_roles` 进行评估，因此为该用户遗留的行确实会提升他们。清理杂散行仍然值得做。
- **开关是 `enableOwnerInstanceAdmin`。** 对于云托管实例，它默认开启；对于自托管实例，它默认关闭，且 Paperclip Cloud 可以通过托管配置文档为整个机群设置它。这是一个 `managed` 级别的标志，在[实验性](../experimental/overview.md)页面上没有卡片，因此 UI 中没有可查找的切换开关——在云托管实例上，这是平台的设置，而非您的设置。

**自己运行 Paperclip？** 此功能不起作用。自托管实例没有受信任的云身份路径——该路径仅在平台设置 `PAPERCLIP_CLOUD_TENANT_SERVER_TOKEN` 时存在——因此标志默认关闭，没有可供其提升的内容。自托管实例上的实例管理员完全按上述描述工作。

#### 提升后的所有者仍然不能做什么

云托管实例上的实例管理员并不等同于机器所有者。少数界面属于平台，其限制在代码中设置：它们适用于云托管实例上的*每个*操作者，包括实例管理员，且没有标志或授权可以解除它们。

- **安装适配器代码。** 在运行时安装或重新安装外部适配器包会被拒绝（`adapter_install_platform_managed`）。适配器代码在服务器进程内运行，因此在云托管实例上，它随平台镜像分发，而不是按需获取。
- **平台配置的环境。** 平台创建的环境不能被更新或删除（`environment_platform_managed`）。唯一的有意例外是仅清除平台标记的元数据补丁——这是针对已不再属于活动平台插槽、但仍保留标记的记录提供的恢复路径。它们的环境变量和凭证形状的配置键永远不会向任何人显示，管理员也不例外；结构细节——提供商、镜像、模板、区域——保持可见，以便环境仍能正确渲染。
- **实例执行模式。** 实例常规设置中的 `executionMode` 由平台固定（`execution_mode_platform_managed`）。保存相同值是可以的，因此回显整个对象的设置表单保持工作——实际更改它会被拒绝，因为切换提供商会使运行搁置在平台从未配置的东西上。
- **手动数据库备份。** 手动触发数据库备份会被拒绝（`database_backups_platform_managed`）。云托管实例上的备份是平台的工作。
- **托管功能标志。** Paperclip Cloud 为机群固定的任何内容保持其锁定徽章。成为实例管理员不会解锁这些切换开关——请参见[实验性功能](../experimental/overview.md)和[云托管实例](../reference/deploy/environment-variables.md#cloud-managed-instances)。

在这些平台拥有的界面之外，提升后的所有者具有上述描述的实例管理员触及范围——实例上的每个公司，包括其不是成员的公司。但有一点不要期望：在云托管实例上将实例管理员权限交给*其他*人不是在实例内部完成的。提升写入实例管理员角色行，而这些行对于通过 Paperclip Cloud 到达的人被故意忽略。那里的提升来自堆栈角色加上此功能，别无其他。

## 值得了解（当前限制）

关于当前人类访问模型的几件事，以免让您感到意外：

- **邀请仅限复制链接。** Paperclip 不发送邀请电子邮件——您创建链接并自行分享。请参见[添加人类队友](../how-to/add-a-human-teammate.md)。
- **移除由管理员驱动。** 没有自助“离开公司”功能；所有者或管理员将成员状态设置为 `suspended` 或归档他们。请参见[成员离职](../how-to/offboard-a-member.md)。
- **个人资料中的电子邮件为只读。** 成员编辑其显示名称和头像；账户电子邮件不能从个人资料页面由用户编辑。
- **尚无 SSO/MFA。** 身份验证通过 Better Auth 使用电子邮件 + 密码。当前版本中没有单点登录、SCIM 目录同步或多因素步骤。
