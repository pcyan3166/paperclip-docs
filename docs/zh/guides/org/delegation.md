# 委派

Paperclip 的强大之处之一，是你不必亲自管理每项工作。设定目标、批准计划后，CEO 会自动把目标拆解为具体任务，并分配给合适的智能体。这就是委派。了解它的运作方式，能帮助你判断何时应介入，何时可以让系统继续运行。

---

## 自动委派如何运作

设定公司目标后，CEO 不会只是确认收到并等待。下一次心跳时，它会阅读目标、制定策略，并将策略提交到你的审批队列。你批准后，委派便会开始：

```
You set a company goal
        ↓
CEO wakes on heartbeat
        ↓
CEO proposes strategy → You approve
        ↓
CEO creates tasks and assigns them to reports
        ↓
Reports wake (triggered by the assignment)
        ↓
Reports execute + post updates in task comments
        ↓
CEO monitors progress + escalates blockers to you
```

每一步都可追踪。所有任务都通过父子层级关联到公司目标，因此你随时可以查看这项工作为什么会发生。

---

## 你负责什么，CEO 自动处理什么

| 你负责 | CEO 自动处理 |
|---|---|
| 设定公司目标 | 将目标拆解为任务 |
| 批准策略提案 | 把任务分配给合适的下属 |
| 批准招聘请求 | 工作需要更细粒度时创建子任务 |
| 查看仪表板 | 在每次心跳中跟进进度 |
| 审阅已完成的工作 | 团队能力不足时申请聘用智能体（需你批准） |
| 工作停滞时介入 | 无法解决阻塞时向你升级 |

你的职责是把握战略方向，而不是管理每项任务。你负责确定方向，并作出系统无法代替你作出的决策；其他事情由系统自主运行。

---

## 批准策略

设定公司目标后，CEO 的第一个操作通常是提交策略提案。这是它为实现目标制定的计划，包括建议的工作流、可能需要的招聘，以及准备创建的首批任务。

你会在 **Approvals（审批）** 页面看到一项类型为 `strategy` 的审批。

审阅策略时，请考虑：

- 计划是否符合你的实际意图？
- 工作流是否合理，优先级是否合适？
- 招聘计划是否与工作范围相匹配？

如果计划看起来合适，就批准。若不合适，请点击 **Request revision（要求修改）** 并发表评论，说明要调整的内容。CEO 会阅读评论、修改计划并重新提交。批准前，你可以来回修改任意多次。

> **建议：** 不要为了尽快开始工作而批准含糊或偏离方向的策略。模糊的批准会导致模糊的工作。花一轮时间要求修改是值得的。

## 批准招聘请求

CEO 判断团队需要更多能力时（例如工程任务需要 CTO、营销工作需要 CMO），会提交一项 `hire_agent` 审批。该请求会出现在审批队列中，完整列出拟聘智能体配置：名称、角色、能力、适配器、预算和汇报对象。

请根据具体情况审查每项招聘请求：

- 这个角色是否符合当前工作需要？
- 建议预算是否适合该智能体的工作量？
- 智能体的汇报对象是否正确？

如果提案中的指令只有一两句话，不必感到意外。现在招聘草案只描述角色——智能体是谁、负责什么；至于如何在 Paperclip 中工作，则交由运行时和已安装的技能处理。如果新智能体需要公司的专属规则，可要求修改，或批准后在它的[说明标签页](./agents.md#instructions-tab)添加。

如果有任何内容不合适，请要求修改；如果看起来正确，则批准。批准后，Paperclip 会创建智能体，并将它排入自动唤醒队列。

> **注意：** 批准招聘请求会创建新智能体并开始产生费用。只有准备好让智能体开始工作时，才批准招聘请求。

## 常见委派模式

### 小型团队：直接委派

有 3–5 位智能体时，CEO 可以直接将工作分配给下属，无需再设一层管理者：

```
CEO
├── CTO         (engineering tasks)
├── CMO         (marketing tasks)
└── Designer    (design tasks)
```

每位智能体独立处理自己的任务并发布进展。CEO 会跟进情况，并在必要时重新分配。

### 较大团队：逐层委派

智能体更多时，经理会继续向下一层委派：

```
CEO
├── CTO
│   ├── Backend Engineer
│   └── Frontend Engineer
└── CMO
    └── Content Writer
```

CEO 把高层级任务分给 CTO 和 CMO，他们再拆解任务，并分配子任务给各自下属。你只需与 CEO 沟通，其余流程会自动运行。

### 按需招聘

你可以先只聘用 CEO，让团队随着工作需求逐步扩充：

1. 设定一个同时需要工程和营销的目标。
2. CEO 提出包含聘用 CTO 和 CMO 的策略。
3. 你批准招聘请求。
4. CEO 向新经理委派工作。
5. 工作范围扩大时，经理可以申请为自己聘用下属。

这样你可以从小团队开始，再根据实际工作扩展，而不是预先规划整支团队。

## 智能体互相委派时的保护措施

委派之所以强大，正因为你不必时刻盯着。但这也有风险：如果智能体把任务交给了错误的对象，任务可能进入无人处理的队列，而你也不会收到提醒。Paperclip 会直接拒绝几类有问题的委派，并向智能体返回可处理的错误，而不是让工作悄无声息地停滞。

两项保护规则只适用于由**智能体**分配任务的情况。你仍然可以自由地将工作分配给任何人，例如为之后准备取消暂停的智能体预先分配任务；界面中也会显示智能体状态。

### 智能体不能将工作分配给已暂停的智能体

已暂停的智能体不会运行。如果另一位智能体给它分配任务（通常是沿 `reports_to` 链向暂停的经理升级），任务虽然会被接收，却无人处理，工作就会悄悄消失。

因此，当分配任务的是智能体，且接收者已暂停时，Paperclip 会拒绝分配并显示冲突消息：

> Cannot assign work to a paused agent. Assign an invokable agent, leave the issue unassigned, or escalate to a board operator instead.

中文释义：无法将工作分配给已暂停的智能体。请分配给可调用的智能体、将 issue 留空不指派，或升级给董事会操作者处理。（以上英文为系统实际返回的固定消息。）

提示中列出了三种解决办法：选择当前能运行的智能体；不指定负责人，让人类来处理；或将问题升级给董事会负责人。对于已终止智能体、仍在等待审批的智能体，以及组织汇报链无效的智能体，原有拒绝规则仍然适用。

### 智能体不能绕成循环，再把工作委派回来

以下是需要拦截的情形：智能体 A 遇到无法完成的工作，例如不能向 GitHub 推送内容，于是为智能体 B 创建子任务。B 也无法完成，就通过新建孙任务来“解决”阻塞，并把任务重新分配给 A。双方都没有获得新的能力，阻塞任务链却越来越长，真正能解决问题的人类始终收不到通知。

如果智能体创建子任务时，将其分配给同一任务链中某项**仍未关闭的祖先任务**的创建者，Paperclip 会以冲突拒绝创建，并返回 `delegation_cycle` 代码。错误消息会指出祖先任务，并说明其他选择：

> Complete the remaining work in your own issue, leave the child unassigned, or escalate to a board operator — do not delegate the work back to the agent that delegated it to you.

中文释义：请在自己的 issue 中完成剩余工作、不要为子任务指派负责人，或升级给董事会操作者处理——不要把工作重新委派给最初委派给你的智能体。（以上英文为系统实际返回的固定消息。）

以下情况不会触发此规则：

- **不影响你本人。** 是否让工作绕过组织架构，由你决定。
- **已关闭的祖先任务不计入。** 只有状态不是 `done` 或 `cancelled` 的任务会被检查；将新工作交给创建过已完成任务的智能体是正常操作。
- **规则检查的是任务的创建者，而非负责人。** 将子任务交给正在处理父任务的人是常见且有效的做法，不会被拦截。

如果在运行记录中看到 `delegation_cycle` 拒绝，应把它视为信号，而非程序错误：两位智能体都缺少一项能力，而其中一方原以为另一方具备。通常缺少的是凭据、工具或权限。解决一次后，整条工作链就能继续。如果缺少的是 GitHub 推送权限，请参阅[将智能体连接到 GitHub 仓库](../../how-to/connect-agent-to-github.md#the-credential-preflight-catches-a-missing-token-before-the-work)，了解如何在消耗工作量之前先检查令牌。

### 升级路径已被暂停时

前面的保护措施会在智能体尝试操作时触发。Paperclip 也会持续提醒你注意升级路径上的危险状态。

智能体会沿 `reports_to` 链向上升级阻塞问题；暂停的经理不会切断这条链，因此下属智能体看起来仍能正常运行，但实际上没有可处理升级的经理。实例导入后最容易出现这种情况，因为导入时默认会暂停所有智能体；你取消暂停工作者后继续处理其他事情，却忘了恢复经理。

Paperclip 会发现此问题。如果某位能运行工作的智能体直接或经由其他经理向上汇报给一位已暂停智能体，它的详情页会显示琥珀色 **Escalation path is paused（升级路径已暂停）** 横幅。该横幅只是警告，不会阻止工作；智能体仍会继续运行，但没有有效的升级对象。横幅会指出哪位经理已暂停，并给出两种解决方式：取消暂停，或更改智能体的汇报对象。

横幅的详细说明和显示位置见[智能体 → 智能体详情页](./agents.md#the-agent-detail-page)。

## 故障排查：CEO 没有委派任务

如果目标已设置，但似乎没有任何进展，请检查以下常见原因。

### 没有创建任务

| 检查项 | 查看内容 |
|---|---|
| **审批队列** | 是否有策略审批等待你审阅？这是最常见的原因：CEO 已提交计划，正在等待批准。 |
| **目标已设置** | 打开公司的 Goals（目标）区域。如果尚无目标，CEO 就没有工作方向。 |
| **CEO 心跳** | CEO 是否已启用心跳？打开 CEO 详情页，检查心跳开关是否打开，以及 **Runs（运行记录）** 标签中是否有近期记录。 |

### CEO 没有把任务分给下属

| 检查项 | 查看内容 |
|---|---|
| **下属已启用心跳** | 打开每位智能体详情页。如果心跳被禁用，CEO 可能会跳过分配，因为它们无法接手工作。 |
| **下属处于活动状态** | 是否有下属已暂停、已终止或处于错误状态？CEO 不会把任务分给无法运行的智能体；智能体向已暂停智能体分配任务会被直接拒绝。 |
| **升级路径横幅** | 打开各智能体详情页，查找琥珀色 **Escalation path is paused（升级路径已暂停）** 横幅。经理暂停后，智能体遇到阻塞时就没有可升级的对象。 |
| **CEO 预算** | 月度预算使用量达到 80% 时，Paperclip 会发出警告；达到 100% 后会自动暂停 CEO。 |

### CEO 把所有任务都分给自己

如果还没有其他活动中的下属，这是预期行为。聘用 CTO 或 CMO 并完成设置后，CEO 就会开始向他们委派工作。

新建 CEO 的角色说明只有一行，不会附带预设的任务分派指南。如果你希望按特定方式分派工作——例如工程任务交给 CTO、营销任务交给 CMO——请在 CEO 的[说明标签页](./agents.md#instructions-tab)中编辑其 `AGENTS.md`。

### 策略已获批准，但没有后续动作

策略获批后，Paperclip 会安排 CEO 自动启动，后续工作通常很快就会开始。若要立即触发，请前往 CEO 详情页并点击 **Run now（立即运行）**。

### 某项任务卡住

1. 打开任务并阅读评论串；负责人可能已经发布阻塞情况或说明。
2. 检查任务状态是否为 `blocked`，并阅读阻塞评论以了解需要什么。
3. 检查负责人状态；它可能已暂停或预算超限。
4. 如有需要，将任务改派给其他智能体，或评论说明当前负责人应如何处理。
