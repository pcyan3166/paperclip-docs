# 成员与访问权限

Paperclip 的大部分功能都围绕**智能体**展开，也就是负责工作的 AI 员工。但公司中也有**人员**：登录系统、查看看板、审批支出、邀请队友并确定方向的人。本指南介绍这些人员如何加入公司、如何决定他们的访问权限，以及人类成员与智能体组织架构之间的关系。

如果你需要按按钮操作的说明，请参阅[公司管理](../../../administration/company.md)；若要查看具体的权限表，请参阅[角色与权限](../../../administration/roles-and-permissions.md)。本页解释这些设计背后的思路。

---

## 人员和智能体共享同一成员模型

理解其余内容的关键是：**人类和智能体都是“主体”（principal），并且共用同一套成员系统。** Paperclip 检查“这个操作者是否有权执行此操作？”时，不会分别使用人类代码路径和智能体代码路径。无论操作者是持有会话的人，还是持有 API 密钥的智能体，系统都会检查同一组信息：（哪家公司、主体类型、哪个主体、所需权限）。

这就是为什么人类和智能体会使用许多相同的界面：

- **邀请链接**既可以邀请人类，也可以让智能体加入（创建链接时由你选择）。
- **加入请求**既可以由人类提出，也可以由智能体提出。
- 人类和智能体的**成员关系**以相同方式存储（但设置中的 **Members（成员）** 页面只列出人员；智能体显示在 **Agents（智能体）** 页面）。
- **权限授予**对人员和智能体的附加方式相同。

日常使用中你主要处理人员一侧；了解这是一套统一系统，也就能理解为什么邀请和审批流程看起来如此对称。

## 角色与权限授予

访问控制分为两个层次，最好分开理解：

- **角色**是一组权限。分配 `Admin` 的简便方式就是给这个人管理员通常需要的几项权限。大多数成员只需设置角色即可。
- **权限授予**是一项单独权限。如果成员只需要额外的一项能力，或需要精确限定为某项能力，可以在角色之外单独勾选权限；也可以不分配角色，仅授予特定权限。

两者以累加方式组合：角色权限包**加上**明确授予的其他权限。明确授予的权限会独立保存在成员记录中，因此即使角色改变也会保留——先提升角色再降级，手动勾选的权限仍会继续生效。完整权限包和权限键列表见[角色与权限](../../../administration/roles-and-permissions.md)；此处只需记住：*角色权限包 + 额外权限，额外权限会持续保留*。

四种角色分别是：**Owner（所有者）**负责公司；**Admin（管理员）**可引导人员和智能体加入，但不能更改其他人的权限；**Operator（操作员）**可执行日常编辑操作，包括管理智能体、技能、工具、邀请和工作分配，但不能批准加入请求或更改其他人的权限；**Viewer（查看者）**只能读取。新邀请默认分配操作员角色。请选择足以完成工作的最低权限；之后随时可以添加权限。

## 人类角色不等于智能体组织架构

这点很容易混淆，所以明确说明：**本页所说的人类角色与 CEO → 经理 → 下属的智能体汇报层级无关。**

- **人类角色**决定谁能使用 Paperclip 产品，例如打开应用、邀请人员、审批支出或修改设置。
- **智能体组织架构**描述智能体之间的汇报关系，例如谁向谁委派任务、预算沿哪个层级汇总。

人类“所有者”并不是组织架构意义上 CEO 智能体的上级，而是负责管理智能体周边公司事务的人。两套模型有意相互独立。智能体一侧的说明见[组织结构](./org-structure.md)。

## 在 Paperclip Cloud 上邀请人员

如果你的组织运行在 Paperclip Cloud 上，可登录人员由 Cloud 管理，而非实例管理。因此，当你是当前 Cloud 组织的所有者或管理员时，成员页面（标题为 **Organization Members（组织成员）**）右上角会显示 **Invite people（邀请人员）** 按钮。点击后会离开当前应用，进入该 Cloud 组织的 **People（人员）** 设置并发送邀请。

以下因素决定你是否能看到此按钮：

- **取决于 Cloud 角色，而非公司角色。** 只有当前 Cloud 组织的所有者或管理员能看到按钮。在 Paperclip 内是公司所有者，或拥有其他 Cloud 组织，都不足以获得此按钮。
- **Cloud 必须能返回角色信息。** Paperclip 确认你的 Cloud 角色后才会显示按钮；如果查询失败，则不会显示。
- **它与 Invites（邀请）标签页分开。** 即使操作员隐藏了应用内的邀请标签页，有权限的用户仍会看到 Cloud 邀请按钮。

自托管实例不会显示此按钮；请使用应用内邀请链接邀请人员，详见[添加人类队友](../../../how-to/add-a-human-teammate.md)。

## 实例管理员：管理整个实例

公司角色只在各自公司范围内生效。另有一个角色可以跨越整个实例：**实例管理员**。实例管理员可管理安装中的每家公司（包括自己不是成员的公司）、提升其他实例管理员，并决定每位用户能访问哪些公司。

如果你把 Paperclip 作为共享平台（例如在一台 VPS 上托管多家公司）而非个人工具，这个角色就很有用。实例进入需身份验证的模式时，会通过[认领董事会管理员](../../../administration/cli-auth.md)流程设置首位实例管理员。之后由实例管理员在“实例访问”界面分配访问权限。此角色独立于公司角色：某人即使不属于任何公司，也可以是实例管理员。

## 每位成员都有个人档案

每位人类成员都有一个**个人档案页**，可通过应用中的 `/u/<user-slug>` 访问。页面既展示身份信息，也呈现活动概况：

- 显示名称、头像和电子邮箱；
- 多个滚动时间段内的活动情况，包括接触、创建和完成的任务，以及评论和活动数量；
- 令牌用量和费用，包括 14 天活动图表，以及产生费用的智能体和服务提供商明细。

如果你想了解队友实际做了什么，或将成本归属到某个人，这个视图很有用。也可以使用 CLI 获取相同信息：`paperclipai profile company-user <user-slug> --company-id <company-id>`（参见 [CLI 参考](../../../reference/cli/access.md#profile)）。

成员可在 **Settings → Profile（设置 → 个人资料）** 中修改*自己的*显示名称和头像。账户电子邮箱不能在个人档案页中修改。

## “离开项目”不等于“失去访问权限”

最后需要区分一个容易混淆的词：“成员关系”。除了公司成员关系，Paperclip 还提供**资源成员关系**，用于标记某位用户是否加入单个项目或智能体。

资源成员关系控制的是**导航，而非授权**。默认情况下，你会“加入”相关资源；离开项目或智能体只会将它从你的个人侧边栏中移除，不会撤销任何人的访问权限，也不会改变任何人可执行的操作。你随时可以重新加入，资源也会重新显示。不要用资源成员关系来控制谁能看到什么；这应由角色和权限授予负责。实现细节见[资源成员关系 API](../../../reference/api/resource-memberships.md)。
