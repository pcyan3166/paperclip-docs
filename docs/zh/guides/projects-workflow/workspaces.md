# 工作区

智能体接手涉及代码或文件的任务时，需要一个执行工作的地方——其中检出了正确版本的代码，目录状态也已准备妥当，供智能体读取、编辑和运行。这就是**执行工作区（execution workspace）**：与特定任务运行关联的项目工作目录快照。

执行工作区让多个智能体可以同时处理同一项目，而不会互相干扰。项目配置为隔离工作后，每个智能体都可以获得自己的副本、分支、目录和运行时上下文，因此一个工作区中的操作不会意外破坏其他工作区。

本指南介绍执行工作区的概念、它们与项目的关系，以及如何使用工作区详情页中的标签、运行时控制和日志检查并管理工作区。

---

## 开始之前：启用工作区

工作区是**实验性**功能；启用之前，**Workspaces** 页面会隐藏。

1. 前往 **Settings → Experimental**。
2. 启用 **Enable Isolated Workspaces**。

启用后，侧边栏会出现 **Workspaces** 项目；任何已有工作区活动的项目中也会出现 **Workspaces** 标签。关闭设置时，侧边栏项目会隐藏，直接访问 `/workspaces` 也会返回问题列表。

> **注意：**这是显示本指南所述全部工作区 UI 的唯一开关，包括项目配置中的执行工作区控制、Workspaces 页面，以及每个问题的工作区模式选择器。如果你不使用隔离工作区，保持关闭即可隐藏这些 UI，避免界面受到干扰。

### Workspaces 页面是什么，以及不是什么

第一次打开 **Workspaces** 时，最常见的意外是页面为空、没有可点击内容。这是正常现象，了解原因会有帮助：

- **不能在此创建工作区。**这里没有 “New workspace” 按钮。首次接手需要工作区的任务时，系统才会自动**配置（provision）**执行工作区（见下一节）。Workspaces 页面用于*检查和管理*已有工作区，而不是手动创建工作区。
- **没有工作发生前，页面会保持为空。**如果还没有智能体运行过隔离任务，你会看到 **“No workspace activity yet.”** 这不是错误——确实没有可显示内容。将任务分配给智能体，让它在隔离工作区中运行，工作区便会自动出现在这里。
- **项目只有存在可展示内容后才会出现。**设置项目主工作区后，它就会显示；其他非主项目工作区在存在运行时服务或配置后才会显示；隔离执行工作区则要等任务在其中运行后才会显示。刚创建且不满足这些条件的项目不会列出工作区，其 **Workspaces** 标签也会保持隐藏。

因此，如果页面看起来空空如也，通常应该“运行一个任务”，而不是“寻找隐藏的创建按钮”——这里没有创建按钮。

## 执行工作区与项目的关系

每个执行工作区都关联到一个项目。项目定义基础配置——代码所在位置、运行方式和默认设置。

任务运行时，Paperclip 会解析该次运行应使用的执行工作区：

1. **心跳触发**，智能体接手任务。
2. **Paperclip 解析工作区**——根据设置新建工作区、复用已有工作区，或使用项目默认工作区。
3. **智能体接收工作区路径**，并在其中工作。
4. 如果使用隔离或可复用工作区模式，**工作区会在运行结束后保留**。

## 工作区模式

为项目启用隔离工作区后，可以选择如何处理问题的工作区：

**Isolated（新建工作区）**
Paperclip 会为此任务创建一个全新的工作副本——在新路径中创建一个从基础分支派生的 Git worktree。智能体在此工作，不会影响其他工作区。任务完成后，你可以审查并合并分支，再归档工作区。

适合会修改代码的任务，例如开发功能、修复问题和开展实验。

**Reuse existing workspace（复用现有工作区）**
任务与其他任务或先前运行共用一个工作区。多个任务可以共用同一工作区，从而处理同一个分支并访问同一组运行中的服务。

如果多个任务关系密切、需要基于相同状态协作，这种方式很有用，例如多个问题共同实现同一功能分支。

**Project primary workspace（项目主工作区）**
任务在项目主检出目录中运行，而不是隔离副本。请谨慎使用——此处的修改会直接影响共享工作副本。

## Paperclip 如何保证复用工作区的一致性

复用工作区很方便，但也会带来一个合理的问题：两个期望环境不同的智能体进入同一个工作区时会怎样？Paperclip 会处理这种差异，避免复用的工作区在无提示的情况下悄悄偏离预期。

- **不会静默沿用环境。**每次任务运行都有预期环境，按以下顺序解析：问题上明确设置的环境始终优先；否则使用项目工作区策略中的环境；否则使用智能体自己的默认环境；最后才使用实例默认环境。（有意固定为本地默认环境的智能体不会被项目策略强行切换离开本地环境——只有问题级环境设置可以改变这一点。）如果运行复用了一个环境与预期不符的工作区，Paperclip 会将其作为冲突明确提示，而不会静默沿用上一个使用者留下的环境。
- **依赖问题会等待工作区完成最终处理。**问题依赖另一个问题时，下游问题的唤醒不会再早于上游工作区完成最终处理。只有依赖的工作区进入一致、稳定状态后，下游任务才会开始，因此不会读取尚未写完的检出目录。
- **接受交互也会等待。**接受计划或审查（`issue.interaction.accept`）时也会先等待工作区完成最终处理，原因相同。

这些行为无需你配置，是隔离和复用工作区本身的一部分。实际效果是：依赖工作和复用工作区每次都能看到一致状态。

> **注意：**执行工作区是本地工作副本。Paperclip 不会代你将其推送到远程 Git 主机——完成的工作通过 Paperclip 审查和合并，而不是在工作区中执行 `git push`。

## 运行时服务

每个工作区都可以配置运行时服务：为了让智能体工作正常而需要在后台运行的进程，例如开发服务器、数据库或构建监视器。

运行时服务需要从工作区 UI 手动控制。心跳触发时，Paperclip 不会自动启动或停止这些服务。

启动工作区服务：

1. 打开项目并点击工作区。
2. 点击 **Start Services**，或启动你需要的具体服务。
3. 服务会在后台运行，UI 中的状态会随之更新。

> **注意：**在一个工作区中启动的服务不会影响其他工作区。每个隔离工作区都有自己的运行时，即使配置继承自项目基础设置也是如此。

## 运行时服务的 HTTPS 预览

运行时服务启动开发服务器时，通常会通过 loopback URL 访问。在受管理工作区中，Paperclip 还可以通过 tailnet 将同一服务发布为真实且证书有效的 `https://<node>.<tailnet>.ts.net:<port>` URL——公开端口与 loopback 应用端口相同。这样，你可以在另一台设备上打开预览，或与同一 tailnet 中的队友分享。

### 查看 HTTPS 状态

Services 控制栏将 HTTPS 暴露状态视为独立于服务进程健康状态的生命周期。这种区分是有意为之：服务进程可能正常运行，但 HTTPS 预览仍在配置中，或配置失败。只有外部 HTTPS 探测实际成功后，预览才会报告为就绪；因此服务灯显示绿色本身并不意味着公开 URL 已经可用。

服务旁会显示以下状态：

- **Provisioning HTTPS…**——服务已启动，Paperclip 正在配置 HTTPS 映射。
- **HTTPS ready**——预览已上线。界面会提供公开 URL、复制 URL 按钮和在新标签页中打开按钮。
- **HTTPS unavailable**——配置失败。控制栏会显示修复提示：“Check the Tailscale broker and node HTTPS configuration.”
- **HTTPS cleanup pending**——之前的映射尚未拆除，端口暂时不能复用；提示为：“Restart the host broker before reusing this port.”

HTTPS 采用失败即关闭策略，Paperclip 不会回退到普通 HTTP 再将其标记为就绪。如果探测失败，预览会保持不可用，而不会静默降级。

### 为服务启用 HTTPS

通常无需进行任何操作：符合条件的运行时会自动启用，因此典型开发服务器会自动获得 HTTPS 预览，无需配置。

若要明确指定，可在服务配置中加入 `expose` 区块，并设置 `type: "tailscale_https"`。几乎所有字段都有默认值，因此以下简写已经是完整声明：

```json
{
  "expose": { "type": "tailscale_https" }
}
```

可识别字段包括：`hostname`（`"auto"`，从本地 Tailscale 节点解析）、`publicPort`（`"same"`，与 loopback 应用端口相同）、`includePaperclipViteHmr` 和 `failurePolicy`（`"fail_closed"`）。省略时会使用各自默认值。`includePaperclipViteHmr` 默认开启，会公开配套 HMR 端口，使 Vite 热重载能通过 HTTPS 源正常工作。若要为服务关闭此功能，可在区块中设置 `type: "none"`（或 `tailscaleHttps: false`）。

> **前提条件：**只有实例位于已安装 HTTPS broker 的 tailnet 上时，HTTPS 预览才可用。如果看到 **HTTPS unavailable**，通常需要处理主机侧辅助程序。操作人员的设置方法见 [Tailscale HTTPS Broker](../../reference/deploy/tailscale-https-broker.md)。

## 打开工作区

作为董事会成员想检查工作区——试用其中运行的应用、检查智能体构建的内容，或排查工作区为何无法启动时，可从工作区详情页进入（**Projects → project → Workspaces → workspace**；受上文 **Enable Isolated Workspaces** 开关控制）。其中的 **Workspace access** 卡片是可靠入口：它会说明工作区当前状态、处于该状态的原因，并提供此刻安全且合理的下一步操作。

该卡片的出现是因为普通的 “Open” 链接曾经会误导用户。数据库已丢失的工作区仍会显示 **Open** 链接，点击后却失败。现在，Workspace access 卡片会显示真实状态和正确后续操作，不会再让你追逐失效链接。

### 查看访问状态

卡片会显示徽标、标题和一个主要操作。主要操作要么是当前可点击的按钮，要么是在 Paperclip 完成后台工作时禁用的等待状态：

- **Provisioning** → “Workspace is not running” → **Start workspace**（或等待期间显示禁用的 **Provisioning** / **Repair in progress**）。
- **Validating clone** → 禁用的 **Validating**——等待检出验证完成。
- **Ready**（或 “Ready — snapshot-local sign-in”）→ **Open workspace**。
- **Degraded** → “Workspace is degraded” → **Repair workspace**（尚无服务在运行时则显示 **Start workspace**）。
- **Repairing** → “Repairing workspace database” → 禁用的 **Repair in progress**——请等待。
- **Failed** → “Database provisioning failed” / “Repair failed” → **Repair workspace**；修复失败时还会提供 **View repair log** 链接。修复失败不会丢失数据：“The pre-repair backup was kept.”

标题下方的易读原因会解释为何显示修复或启动操作，而不是 **Open workspace**。卡片可能指出：尚无健康的运行时服务发布 URL；运行时发布的 URL 无法由 Paperclip 打开；克隆的数据库尚未准备好接受登录；隔离数据库没有响应；克隆未恢复任何公司或问题记录；无法读取克隆产品表；或没有任何克隆用户拥有有效的公司成员身份。遇到这些情况时，卡片会提供 **Repair workspace** 或 **Start workspace**，而不是一个点击后只会失败的链接。

### “Open workspace”的作用——一次性登录交接

工作区处于 **Ready** 且提供登录交接时，卡片会注明：“Uses a single-use login handoff — no password needed.” 点击 **Open workspace** 会调用 `POST /api/execution-workspaces/{id}/login-handoff`，生成一个短时有效、**只能使用一次**的票据。隔离工作区会用该票据换取仅限其自身实例的会话，因此打开受管理工作区无需使用克隆的密码。

端点会返回供你导航的 `url`，不需要保存它。工作区会以重定向响应此 URL，因此票据不会留在浏览器历史记录中。如果想指定工作区中的落地位置，可在可选请求体中传入 `{ "next": "<same-origin path>" }`；任何不属于同源路径的值都会回退为 `/`。

### 快照本地登录备用方式

如果实例未配置登录交接，或当前会话没有可用于登录的克隆用户，卡片会改为注明：“Signs in with the snapshot-local credentials captured when this clone was made.” 两种拒绝原因会触发此备用方式：实例没有配置工作区登录交接，或会话中没有克隆的董事会身份。此时你使用的是克隆时冻结的凭据，而不是一次性票据。

## 工作区继承

创建项目时，可以为其定义基础运行时配置——如何启动服务、需要哪些环境变量以及运行哪些命令。

默认情况下，隔离执行工作区会继承该配置。如果某项任务需要的设置与项目默认值不同，可在具体工作区中覆盖相应设置。

继承机制回答的是“如何运行？”——但实际运行进程始终属于具体工作区。即使两个工作区继承相同配置，它们运行的进程仍相互独立。

## 工作区生命周期

执行工作区会持续保留，直到你明确归档或拆除它。这意味着：

- 智能体的分支状态、未提交修改和正在运行的服务会跨心跳保留。
- 多次心跳可以继续使用同一个工作区，并从上次停止的位置接着工作。
- 共享工作区会累积多个任务的修改。

完成工作区工作后：

1. 审查智能体的工作（合并分支、批准修改等）。
2. 点击工作区上的 **Archive**。
3. Paperclip 会根据工作区模式和项目设置清理工作区。

> **警告：**归档含有未合并分支或未提交内容的工作区，会导致这些工作丢失。归档前，请确认已审查并合并所有需要保留的内容。

## 什么时候会用到工作区

对大多数董事会操作人员来说，执行工作区是在后台发生的事情。无需为每个问题单独配置；普通智能体执行普通工作时，默认设置通常足够。

以下情况应多加留意：

- 多个智能体要处理同一个代码库，需要避免冲突。
- 智能体需要特定服务运行才能完成工作。
- 希望在合并前先通过分支审查智能体的修改。
- 某个任务需要从前一个任务停止的位置继续。

## 工作区列表

有两个位置可以查看工作区，数据相同，只是视角不同：

- **Workspaces 侧边栏项目**打开公司级视图，并按项目分组。你会看到所有有工作区活动的项目及其工作区。正在运行服务的项目会排在前面。
- **项目的 Workspaces 标签**（打开项目并点击 **Workspaces**）显示限定于该项目的同一列表。项目有工作区活动后，该标签才会出现。

无论从哪里进入，都能看到项目主工作区以及 Paperclip 配置的隔离执行工作区。如果尚未配置任何工作区，公司级视图会显示 **“No workspace activity yet.”**。

![公司级 Workspaces 页面按项目分组：Website 项目的隔离执行工作区（带运行中的服务和关联任务）位于其主“main”工作区上方](../../../user-guides/screenshots/light/workspaces/list.png)

每个工作区都以卡片显示：

- **类型**——*Execution workspace* 或 *Project workspace*。
- 工作区**名称**，以及对应的**分支**和**路径**。
- 正在运行的**服务**（例如 `1/1 services`），以及服务公开 URL 时显示的实时链接。
- 执行工作区的**状态**（active、idle、in review、archived 或 cleanup failed），以及 **Close workspace** / **Retry close** 控件。
- 曾在此工作区运行的**关联任务**，以及最近更新时间。

工作区有运行时配置时，卡片还会直接提供 **Start services** / **Stop services** 按钮。点击工作区名称可打开详情页，在其中检查和编辑配置、控制运行时服务、查看操作日志，以及查看所有曾在此工作区运行的任务。

详情页标题会显示工作区名称，右侧提供服务的快速启动/停止/重启控件。标题下方分为以下标签：

1. **Tasks**——所有曾在此工作区运行的任务（默认标签）。
2. **Services**——工作区的运行时服务和一次性作业，提供启动/停止/重启及运行控件。
3. **Configuration**——工作区设置、工作区上下文和具体位置。
4. **Runtime logs**——运行时操作和清理操作的历史记录。
5. **Routines**——使用工作区专属变量的例程，可在此工作区中运行。

已安装插件可以增加自己的标签，例如 workspace-diff 插件会添加 **Changes** 标签。系统会按工作区记住你上次选中的标签；如果某个工作区总是从 Runtime logs 开始查看，Paperclip 会记住这一选择。

## Services 标签

**Services** 标签是运行时行为的控制面板：可管理需要在后台持续运行的服务，以及要在此工作区中触发的一次性作业。（标签上方的标题也提供快速启动/停止/重启按钮，因此在任意标签中都可以操作服务。）

![Services 标签](../../../user-guides/screenshots/light/workspaces/services.png)

此处的操作受两项规则约束：

1. **必须设置工作目录。**Paperclip 在工作区中运行的每条命令都需要一个绝对路径作为工作目录。如果工作区的 `cwd` 为空，操作按钮会被禁用，并提示你先修正该字段。在 Configuration 标签中填写 **Working directory** 并保存后，控件会重新启用。
2. **服务需要运行时配置。**只有项目工作区或当前执行工作区的配置链上存在运行时配置，才会显示服务命令。如果两处都没有配置，服务列表会保持为空并显示简短说明；只要已定义作业且设置了 `cwd`，作业仍可能运行。

该标签将命令分为两个区域：

- **Services**——长时间运行的进程，例如 `pnpm dev`、Postgres 容器或构建监视器。每项服务都显示启动、停止和重启控件，以及最近观察到的状态。
- **Jobs**——一次性命令，例如 `pnpm db:migrate` 或测试运行器。每项作业都有一个运行操作。

Paperclip 正在执行操作（例如启动服务）时，控件会显示等待状态并阻止重复操作。成功时会显示简短确认，例如 “Workspace service started.” 或 “Workspace job completed.”；失败时会以红色显示适配器返回的错误。无论成功还是失败，完整历史都会写入 Runtime logs 标签。

## Configuration 标签

Configuration 标签用于检查和编辑定义该工作区的所有内容——磁盘路径、关联仓库和分支、配置及拆除命令，以及当前执行工作区专属的运行时覆盖。

![Configuration 标签](../../../user-guides/screenshots/light/workspaces/configuration.png)

### 工作区设置

**Workspace settings** 卡片包含可编辑的工作区字段。Paperclip 配置工作区时通常会填好大部分内容；一般只有智能体或项目迁移、分支重命名或配置脚本变化时，才需要修改它们。

- **Workspace name**——用于列表、面包屑和通知中的易读名称。
- **Branch name**——工作区检出的 Git 分支。隔离 worktree 通常使用类似 `PAP-946-workspace` 的分支名。
- **Working directory**——磁盘上的绝对路径，智能体会在此处运行命令。为空时 Paperclip 无法为该工作区运行本地命令；这是最需要保持正确的字段。
- **Provider path / ref**——工作区提供程序使用的路径或引用。Git worktree 使用 worktree 路径；其他提供程序使用其所需引用。
- **Repo URL**——工作目录克隆自哪个远程 URL。UI 用它链接到 GitHub/GitLab。
- **Base ref**——工作区派生自哪个引用，例如 `origin/main`。
- **Provision command**——Paperclip 准备此执行工作区时运行的命令，例如克隆 worktree 并安装依赖的脚本。
- **Teardown command**——执行工作区归档或清理时运行的命令。
- **Cleanup command**——可选的工作区专属清理步骤，会在 teardown 前运行，例如终止卡住的 `vite` 进程。

卡片右上角有 **Close workspace** 按钮。关闭时会运行 teardown 和 cleanup 命令；根据命令退出状态，工作区会进入 `archived` 或 `cleanup_failed`。如果上次关闭操作以 `cleanup_failed` 结束，按钮会变为 **Retry close**。

命令字段下方有 **Runtime config source** 提示，可快速判断该执行工作区：

- 正在继承项目工作区的运行时配置；
- 使用自身配置覆盖了项目工作区配置；或者
- 尚无任何运行时配置。

工作区覆盖了继承的运行时配置时，可点击 **Reset to inherit** 移除覆盖，恢复项目工作区默认值。

少数情况下需要编辑原始运行时 JSON，可展开 **Advanced runtime JSON** 面板。面板包含：

- 一个复选框 **Inherit project workspace runtime config**，用于切换覆盖和继承模式。
- 一个 JSON 文本框，可编辑工作区的 `commands` 对象。既接受旧版 `services` 数组，也接受更新的 `commands` 数组（支持服务和作业）。

在 **Workspace settings** 卡片中所作修改会暂存在本地，直到点击 **Save changes**。**Reset** 按钮会恢复为 Paperclip 当前保存的值，因此无需重新加载页面即可撤销未完成的修改。

### 工作区上下文

**Workspace context** 卡片在 UI 中标记为 “Linked objects”，会显示与当前执行工作区关联的其他 Paperclip 实体：

- **Project**——该工作区所属项目。
- **Project workspace**——配置此执行工作区时依据的项目级工作区。运行时配置继承会沿此关系解析。
- **Source issue**——最初触发创建此工作区的问题（如果有）。点击可打开问题详情。
- **Derived from**——如果此工作区从另一个执行工作区分拆或派生而来，会显示指向原工作区的链接。这是 Paperclip 表示共享代码谱系的后续 worktree 的方式。
- **Workspace ID**——原始标识符，以等宽字体显示，可复制用于 API 调用或调试。

通过此卡片可快速返回项目、触发工作的源问题，或当前工作区派生自的父工作区。

### 具体位置

**Concrete location** 卡片汇总工作区的物理位置和 Git 状态。它不会提供新字段——这些内容都在 Workspace settings 中——但此处格式便于快速浏览和复制，而非编辑。

- **Working dir**——绝对路径，并带有复制按钮，可粘贴到终端中。
- **Provider ref**——提供程序专属引用或 worktree 路径。
- **Repo URL**——设置为有效 `http(s)` URL 时，会显示可点击的远程链接。
- **Base ref**——分支所依据的起始引用。
- **Branch**——当前分支名。
- **Opened**——Paperclip 首次打开该工作区的时间。
- **Last used**——智能体最近一次与该工作区交互的时间。
- **Cleanup**——Paperclip 已安排清理该工作区时，此处显示满足清理条件的时间和原因；否则显示 `Not scheduled`。

Workspace settings、Workspace context 和 Concrete location 共同提供了回答“这是哪个工作区、位于何处、关联了什么？”所需的全部信息。

### 使用运行时配置覆盖

项目默认值和工作区专属需求有时会互相冲突；Paperclip 使用两层继承模型解析运行时配置：

1. **项目工作区**定义基础运行时配置。除非明确覆盖，否则它会应用于从该项目工作区创建的每个执行工作区。
2. **执行工作区**可以继承基础配置，也可以使用自己的 `workspaceRuntime` 对象进行覆盖。

Configuration 标签中的 **Runtime config source** 提示会说明当前采用哪种配置：

- **Execution workspace override**——此工作区使用自己的运行时配置，并忽略项目工作区提供的配置。需要为特定 worktree 使用不同端口、开发命令，或添加不应出现在所有工作区中的作业时，可使用此选项。
- **Project workspace default**——此工作区按原样继承项目运行时配置。这是常见情况，也应优先采用；覆盖配置会产生漂移，应仅在必要时使用。
- **None**——两层都没有定义运行时配置，因此 Paperclip 无法启动服务。如果有已配置的作业，仍可能运行；但 Services 标签不会显示服务。

若已添加覆盖但想恢复继承，点击 **Reset to inherit** 即可清除覆盖，让工作区回退到项目工作区配置。如果项目工作区本身没有运行时配置，该按钮会禁用；否则执行工作区会被重置为 “None”。

**Advanced runtime JSON** 面板刻意隐藏在折叠控件后。编辑原始 JSON 属于高级操作；对大多数团队来说，在项目级配置服务就足够了。确实需要编辑时，面板接受以下两种结构：

- 旧版 `{ "services": [...] }` 数组，用于向后兼容。
- 新版 `{ "commands": [...] }` 数组，其中条目使用 `kind: "service"` 或 `kind: "job"`；新工作区应采用此结构。

点击 **Save changes** 时，Paperclip 会验证 JSON。如果无法解析或内容不是 JSON 对象，界面会显示内联错误并中止保存。

## Runtime logs 标签

切换到 Runtime logs 标签，即可查看 Paperclip 对此工作区实际执行的操作：运行过哪些命令、运行时间、退出方式以及输出内容。

![Runtime logs 标签](../../../user-guides/screenshots/light/workspaces/runtime-logs.png)

在 **Recent operations** 标题下，每一项都代表一次工作区操作：

- 运行的**命令**（如果是生命周期步骤而非命名命令，则显示对应**阶段**）。
- **开始时间**，以及操作完成时显示的**结束时间**。
- 简短的 **stdout** 摘录；命令失败时则显示简短 **stderr** 摘录。stderr 会以红色突出显示，便于快速发现失败。
- 右侧的**状态标记**，显示操作正在运行、已成功或已失败。

该标签包含两类操作：

- **运行时操作**——从 Services 标签（或标题栏快捷控件）触发的服务启动、停止、重启和一次性作业。
- **清理操作**——Paperclip 准备或关闭工作区时运行的 provision、teardown 和 cleanup 命令。

尚未发生任何操作时会显示 “No workspace operations have been recorded yet.”。操作日志加载失败时，服务器错误会以红色显示。

智能体报告服务未启动、作业失败或工作区无法关闭时，可首先查看此标签。多数情况下，stderr 摘录足以诊断问题；时间戳也方便将失败的心跳运行与具体出错命令对应起来。

### 操作与用户行为的对应关系

刚开始使用 Runtime logs 标签时，了解哪些 UI 操作会生成哪些日志项会很有帮助：

- 在 Services 标签中点击服务的 **Start**，会创建一项操作，记录服务命令和 `started` 阶段；成功后，如果服务仍在运行，状态会显示为运行中；如果服务立即退出，则显示为已完成。
- 点击服务的 **Stop** 或 **Restart**，会生成一项简短操作，记录服务如何停止或重启。
- 点击作业的 **Run**，会生成一项记录其命令的操作；最终状态取决于作业退出码。
- 从 Configuration 标签点击 **Close workspace** 时，会依次运行 cleanup 命令和 teardown 命令。两者分别成为独立操作，因此关闭最终进入 `cleanup_failed` 时，你能判断究竟是哪一步失败。
- **Provision** 操作会在 Paperclip 首次准备工作区时自动生成；不会由 UI 触发，但排查首次启动问题时可以在此处查看。

如果摘录无法说明失败原因，请记住内容可能已截断。可在磁盘上进入底层 worktree，从该目录手动重新运行命令，并将完整输出与摘录比较；两者的差异通常能指出智能体运行环境与当前 Shell 之间的环境或权限差别。

## Tasks 标签

Tasks 标签会列出所有曾在此执行工作区中运行的问题——不只有创建工作区的源问题，还包括后续任务、重试任务以及继承此工作区的相关任务。

![Tasks 标签](../../../user-guides/screenshots/light/workspaces/issues.png)

此列表使用与主问题视图相同的组件和筛选器，因此可以快速查看：

- 问题标识符、标题、状态、优先级和负责人。
- **实时运行指示器**——当前正针对此工作区运行心跳的问题会突出显示，便于查看正在进行的工作。
- 可内联执行的问题状态更新、重新分配，以及打开问题详情页等操作。
- 此视图的本地状态——显示哪些列、采用何种排序——会保存在 `paperclip:execution-workspace-issues-view` 键下，因此不同执行工作区可以有不同的首选布局。

此标签可回答三个常见问题：

- “这个工作区实际用于哪些工作？”——滚动查看列表。
- “现在是否有任务在此工作区运行？”——查看是否有实时运行高亮。
- “现在是否可以安全归档工作区？”——如果这里的所有问题都是 `done`、`cancelled` 或其他非活动状态，通常可以安全归档。

关闭工作区前，如果需要重新分配或重新安排列表中的问题，点击进入该问题、完成修改并返回即可；列表会自动更新。

### 源问题与关联问题

Tasks 标签和 Configuration 标签的 Workspace context 卡片会显示两种不同关系，注意区分：

- **源问题（source issue）**是最初导致 Paperclip 配置此工作区的那个问题。它保存在工作区自身，并显示在 Workspace context 卡片中。由特定任务创建的隔离 worktree 通常会将启动整个流程的任务作为源问题。
- Tasks 标签中的**关联问题（linked issues）**是曾附加到此工作区的所有问题，包括源问题、继承工作区的后续子问题，以及 `inheritExecutionWorkspaceFromIssueId` 指向此工作区的问题。

判断能否安全归档时，应检查完整的关联列表，而不只是源问题。归档工作区会一并移除分支状态；仍引用该工作区的后续问题下次运行时将无法获得有效的 `cwd`。

## 归档与清理

在 Paperclip 中关闭工作区分两步完成：

1. **Cleanup**——如果配置了 cleanup 命令，会先运行。此步骤用于停止遗留开发服务器、释放端口，以及执行其他确保 teardown 可成功的操作。
2. **Teardown**——随后运行 teardown 命令，拆除工作区本身。对于 Git worktree，通常会移除 worktree 目录并修剪分支；其他提供程序则执行其定义的清理操作。

两步都成功后，工作区会进入 `archived` 状态，并从默认工作区列表中消失。如果任一步失败，工作区会进入 `cleanup_failed` 状态——仍然存在并可见，且 **Close workspace** 按钮会变为 **Retry close**，以便修复问题后重试。成功重试之前，工作区会保留关闭操作开始前的状态。

一些实用建议：

- 关闭前先查看 Runtime logs 标签，检查是否仍有操作在运行。清理时会停止状态为 `running` 的服务，也会终止真正正在执行的作业——请确认不会中断重要操作。
- 在 **Tasks** 标签检查是否仍有与工作区关联且状态为 `in_progress` 的问题。只有这些问题都已完成、取消或迁移到其他工作区后才归档。
- 如果智能体在分支上有未提交修改，teardown 会将其删除。请先合并分支，或提交/暂存你想保留的内容。

Concrete location 卡片中的 **Cleanup** 行会说明 Paperclip 是否已为工作区安排自动清理（例如空闲时间超过保留期限），以及清理原因。如果看到意料之外的计划清理，请检查项目的工作区生命周期设置以了解原因。

## 故障排查清单

遇到异常时，提交错误报告前先逐项检查：

- **`cwd` 是否已设置且正确？**没有绝对工作目录就无法运行任何本地命令。在 Configuration → Workspace settings → Working directory 中检查。
- **分支是否仍然存在？**如果有人在 Paperclip 外部删除了分支，智能体检出时会失败。请重新创建分支或更改引用。
- **运行时配置是否实际生效？**查看 Configuration 标签中的 Runtime config source。如果显示 “None”，就没有可用的服务命令。
- **端口是否被另一个工作区占用？**同一台机器上的两个隔离 worktree 若继承相同开发服务器配置，都会尝试绑定同一端口。请为其中一个覆盖端口，或避免同时启动。
- **先前的关闭操作是否失败？**工作区处于 `cleanup_failed` 时，在重试关闭或手动解决底层问题并再次重试前，状态会一直未清理。
- **智能体使用的是否是正确工作区？**创建后续任务时，请确保子问题设置了 `parentId` 或 `inheritExecutionWorkspaceFromIssueId`，以便 Paperclip 能将其解析回此工作区。

大多数工作区问题都可以归结为以上六项。

### 任务在智能体开始前停止

有一种工作区问题会在任务讨论串中显示通知，而不是显示为失败运行：

- **起始分支不存在。**如果任务要求检出仓库中不存在的分支（例如仓库只有 `master`，任务却指定 `main`），通知会说明未找到该分支。Paperclip 能读取仓库默认分支时，会提供 **Use `<branch>` & retry** 按钮。否则，请选择 **Choose another branch**，在 **Starting branch** 中输入分支，然后点击 **Save branch & retry**。此操作只会更改该任务的起始分支，Paperclip 不会静默切换分支。

## 隔离与 Git worktree

Paperclip 默认使用从项目工作区基础引用派生的 **Git worktree** 作为“隔离”执行工作区。如果你以前没有使用过 Git worktree，实际含义如下：

- Worktree 是同一仓库的第二个（或第三个、第十个）检出目录，位于不同路径，并检出各自的分支。
- 它们与主检出共享底层对象数据库，因此创建 worktree 的成本较低——无需完整重新克隆，也不会在磁盘上复制整个历史记录。
- 每个 worktree 都有独立的工作目录，因此不同 worktree 中的智能体不会意外覆盖彼此未提交的修改。

Paperclip 配置隔离工作区时会：

1. 在项目工作区的 worktree 目录下选择一个路径。
2. 从已配置的基础引用（例如 `origin/main`）创建新分支。
3. 将该分支检出到新的 worktree 路径。
4. 运行 provision 命令，在智能体开始前准备好依赖、环境文件和其他 worktree 专属设置。

从智能体角度看，这些步骤都是透明的——它只会获得一个可以读取、编辑和运行的 `cwd`。作为董事会操作人员，你可以在 Configuration 标签的 Concrete location 卡片中查看确切路径和分支，也可自行进入目录检查或调试。

### 哪些情况不值得隔离

隔离会产生额外成本：每个 worktree 都需要自己的 `node_modules`（或等价依赖目录）、开发服务器和数据库迁移。大型项目中的成本会不断累积。以下任务通常不需要隔离工作区：

- **纯只读任务**——研究、总结或审阅文档。使用项目主工作区或复用工作区。
- **只修改问题元数据的任务**——分流、估算、分配。这些任务甚至不需要检出代码。
- **多个任务协作完成同一功能**——复用一个工作区，让所有任务在同一状态上累积修改。

智能体确实会修改代码、且你希望分别审查修改，或希望并行开展多个实验而不互相影响时，隔离才最有价值。

## 一览工作区可观测性

将各标签的作用归纳起来，详情页可回答以下常见问题：

- “这是哪个工作区，位于何处？”→ Configuration 标签的 Concrete location 卡片。
- “工作区为何存在，关联了什么？”→ Configuration 标签的 Workspace context 卡片。
- “由谁决定此处服务如何运行？”→ Configuration 标签的 Runtime config source 提示。
- “此工作区实际发生了什么？”→ Runtime logs 标签。
- “谁在此工作区运行过任务？”→ Tasks 标签。
- “现在有东西在运行吗？”→ Services 标签（或标题栏快捷控件）查看服务状态；Tasks 标签查看实时运行指示器。

页面顶部的面包屑也会将各部分联系起来：**Projects → {project name} → Workspaces → {workspace name}**。从任意工作区详情页都可以一次点击返回项目、两次点击返回工作区列表。

## 常见工作流

以下是几种常见的具体模式：

**开始开发新功能**

1. 创建问题并分配给负责执行的智能体。
2. 智能体检出任务时，让 Paperclip 自动配置隔离工作区。
3. 智能体完成工作且分支已就绪后，按你平时的 Git 工作流审查分支。
4. 合并后返回 Workspaces 标签并归档工作区。

**从关闭失败中恢复**

1. 打开工作区并查看 Runtime logs 标签，找出失败的命令。
2. 修复底层问题，例如卡住的进程、缺少的权限，或假设 Shell 不正确的命令。
3. 点击 **Retry close**，并确认工作区进入 `archived` 状态。
4. 如果重试仍失败，进入 worktree 目录并手动运行 teardown 命令。

**执行数据库迁移**

1. 在工作区运行时配置中创建作业（例如 `db:migrate`）。
2. 打开工作区，在 Services 标签中点击该作业的 **Run**。
3. 等待 Runtime logs 中出现操作记录并显示成功状态。
4. 将结果证据关联到问题；操作时间戳通常就足够。

**在多个任务间复用工作区**

1. 创建后续问题时，如果它是子任务则设置 `parentId`；如果它是应共享同一工作区的同级任务，则设置 `inheritExecutionWorkspaceFromIssueId`。
2. Paperclip 会在检出任务时将新问题关联到现有工作区。
3. 在工作区的 Tasks 标签中可以看到新问题和原问题并列显示。

这些只是默认模式，请根据团队的实际工作方式调整。

## 准备就绪

执行工作区为智能体提供隔离且保留状态的环境，以便可靠地处理文件类工作。Workspace 列表显示项目已配置的所有工作区；Configuration 标签让路径、仓库和运行时配置与实际情况保持一致；Runtime logs 标签显示实际运行过的内容；Tasks 标签则显示谁使用过该工作区。
