# 任务看护器

有时智能体会因为错误原因停止工作：误读阻塞事项、没有实际证据就宣布任务“完成”、接受过期的计划确认，或遇到可恢复错误后放弃。发生这种情况时，没有任何机制会唤醒其他人，任务树就会安静地停在那里。

**任务看护器**是一位负责复查已停止任务树的智能体；如果停止工作是个错误，它会让任务重新运转。你将看护器附加到一项任务后，它会监控该任务及其后代任务。子树中所有任务都已停止，且没有继续推进的路径时，Paperclip 会唤醒看护器，让它检查证据并判断：工作确实应该停止，还是应该继续。

可以把它理解成对停止工作的第二次检查，但不会重新运行原负责人。它的工作重点是验证而不是执行：根据任务讨论串中的实际内容核实其他智能体提出的说法，然后接受停止状态，或恢复有效的工作路径。

> **提示：** 看护器需按任务单独选择启用。没有一个全局的“监控所有任务”开关；你可以自行选择哪些任务树值得额外检查。

---

## Paperclip 中有三种“看护器”

Paperclip 的不同位置都会用到 watchdog 一词，请区分以下三种含义：

- **任务看护器**（本页）——由*你*指定给某项任务的智能体；只有受监控子树整体停止后才触发。可配置。
- **运行静默看护器**——自动监测单个*正在运行*的智能体是否长时间没有输出。无需配置或设置。活动运行摘要在 5 分钟无输出后显示 **suspicious（可疑）** 等级，15 分钟后显示 **critical（严重）**。它本身不会执行任何操作，也不会自动取消运行；目前也不会创建评估任务、恢复操作、评论或唤醒请求。（可查看适配器的不活动设置，例如 Codex 本地适配器的 `outputInactivityTimeoutMs`。）
- **存活性恢复**——自动重启停滞的、由智能体负责的任务。

只有第一种需要你手动启用。

## 看护器何时启动

只要还有可继续的工作，看护器就会保持休眠。只有受监控子树中的**每一个叶子任务**都已停止（完成、取消、阻塞、进入审查，或正在等待交互），且没有后续路径可走时，看护器才会启动。

![看护器生命周期：附加看护器、工作运行、子树停止、创建审查任务、发布结果并记录状态指纹](../../../user-guides/screenshots/diagrams/task-watchdog-lifecycle.png)

此时，Paperclip 会把任务树和一项指令交给看护器：将每个停止的叶子任务都视为需要核实的*说法*，而不是直接相信的事实。之后，看护器会：

- **不干扰确已完成的叶子任务**，并简短记录检查了什么。
- 如果叶子任务实际上尚未完成，**恢复工作路径**：重新打开任务、重新分配负责人、发表评论说明可执行的下一步、在受监控子树中创建后续子任务，或接受符合条件的计划确认。
- **确认真实阻塞**，并留下清晰的等待状态，写明谁可以解除阻塞以及接下来会发生什么。

看护器不会轻信“我做不到”或“正在等待审批”之类的说法；这正是设置看护器的原因。

审查结果会回到被监控任务的讨论串中，因此谁检查了什么、发现了什么，都与工作本身保存在一起。活动动态会标记通过看护器审查进行的更改，让你之后查看讨论串时能区分看护器和任务负责人采取的操作。

Paperclip 还会为已审查的停止状态生成指纹。如果上次检查后情况没有变化，就不会再创建新的审查任务。同一停滞任务树按不同状态检查，而不是每次扫描都检查，因此讨论串中不会出现对同一段沉默的重复审查。

## 设置看护器

看护器包含三部分：

| 字段 | 必填 | 说明 |
|---|---|---|
| 受监控任务 | 是 | 附加看护器的任务，默认就是当前正在编辑的任务。 |
| 看护器智能体 | 是 | 同一家公司中任意可被调用的智能体。不能是已暂停、已终止或预算耗尽的智能体。 |
| 指令 | 否 | 任意文本。可用于限定审查重点或拒绝特定捷径，但不能扩大看护器的权限。 |

每项任务**最多只能有一个活动看护器**。重新分配看护器智能体或编辑指令时，看护器记住的已审查状态会重置，因此下次扫描将从头开始。

### 在应用中设置

有两个位置可以配置：

- **新建任务对话框**——打开三点菜单，选择 **Watchdog（看护器）** 行。选择智能体，也可以填写指令。看护器会和任务一起创建，对话框底部会用标签显示你的选择。
- **任务属性**——找到 **Monitor（监控器）** 旁的 **Watchdog（看护器）** 行。未配置时显示 `Set watchdog`；配置后显示智能体名称和指令预览。点击该行打开编辑器，选择智能体、撰写指令，然后点击 **Set watchdog（设置看护器）** 或 **Update（更新）**。也可以点击 **Remove（移除）**。看护器启动审查任务后，此行会显示一个可直接打开该任务的小标记。

### 通过 API 设置

```http
GET    /api/issues/:issueId/watchdog
PUT    /api/issues/:issueId/watchdog   { "agentId": "...", "instructions": "..." }
DELETE /api/issues/:issueId/watchdog
```

`PUT` 是 upsert 操作，会创建看护器或更新现有看护器。`DELETE` 会停用看护器（保留记录用于审计，不会彻底删除）。三个端点都要求对受监控任务有写权限，并会记录一条活动（`issue.watchdog_created`、`issue.watchdog_updated` 或 `issue.watchdog_removed`），包含操作者和运行 ID。

## 编写有效的指令

好的指令会告诉看护器*应检查哪些证据*，以及*不应走哪些捷径*。例如：

> 接受任何叶子任务为已完成之前，请确认评论中关联了一次成功的 CI 运行。如果没有，请重新打开该任务并要求提供 CI 结果。

> 如果计划提出超过五个子任务，不要在没有我审阅的情况下接受。请让任务保留在审查状态并通知我。

> 如果叶子任务因为等待营销团队而受阻，可以接受等待状态，但请确认阻塞说明中写明了谁能解除阻塞。

指令**不能**让看护器访问受监控子树之外的内容、批准董事会级决策、扩大看护器能解决的交互类型，或放宽安全限制。无论指令内容是什么，服务器都会强制执行这些边界。

---

## 看护器不能做什么

看护器受服务器强制的硬性限制约束。自定义指令可以收紧限制，但不能放宽：

- 活动范围**仅限受监控子树**，不能更改该树之外的任务，也不能跨公司操作。
- **不能批准仅限董事会作出的决策**，例如支出、招聘或涉及安全的交互；也不能绕过要求指定审查者或审批者的执行策略阶段。
- **不能修改自己的配置**，不能为同一任务树创建另一个看护器，也不能自行唤醒。

任何越界操作都会在 API 层被拒绝。看护器必须改用合规方式：发表评论、在子树中创建后续任务、留下有效的等待状态，或将问题升级给人类。

## 看护器、审批和执行策略

Paperclip 有三种监督机制，各自回答不同的问题。

审批是人工关卡：操作发生前必须有人同意。执行策略是分阶段审查：工作必须经过预设的审查阶段，才能算作完成。这两者都是工作必经的检查点。

看护器则不处在工作路径中，而是在旁观察，只有工作路径停止时才介入。审批和执行策略能拦截你提前设定的关卡上的问题；看护器能够发现两者都无法发现的情形：工作一直没有到达关卡。

三种机制可以组合使用。长周期任务可以通过执行策略审查交付物，通过审批控制高成本操作，同时由看护器确保任务持续推进并到达这些关卡。

## 何时不该使用看护器

如果任务树有许多叶子任务，你想在相信“一切正常”之前再检查一次；原负责人经常过早宣布完成；或工作足够重要，值得多花一次智能体运行来避免误判停止，看护器就很有价值。

以下情况不适合使用看护器：

- **监测单个运行进程是否沉默**——使用自动的运行静默看护器，无需设置。
- **恢复停滞的智能体任务**——这也是自动处理的。
- **把关董事会级或安全敏感决策**——看护器不能处理这些审批。
- **代替执行策略阶段中的人工审查者**——看护器不能绕过指定参与者。

如果你真正想要的是“完成时提醒我”，请使用[例程](../../../guides/projects-workflow/routines.md)或任务讨论串中的交互机制。
