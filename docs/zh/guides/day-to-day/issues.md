# 问题

Paperclip 中的工作以**问题（issue）**表示。每个问题都是一项独立工作，由智能体领取、执行并完成。每个问题都能追溯到公司目标，因此智能体始终知道自己工作的缘由。

大多数情况下，CEO 智能体会根据战略自动创建问题。不过，有时你可能希望直接给智能体安排一项具体工作，例如撰写某份文档、调查特定问题，或审查刚从客户处收到的内容。这时就可以手动创建问题。

产品界面使用 **task** 和 **issue** 指代同一项工作。界面将页面称为 **Tasks**；底层 API 路由为 `/api/issues`。

![任务页面，按父任务嵌套显示公司的所有任务](../../../user-guides/screenshots/light/issues/list.png)

## 何时自己创建问题，何时交给 CEO 处理

以下情况适合手动创建问题：

- 有一项具体、明确的请求，当前战略尚未涵盖。
- 需要把智能体注意力转向紧急事项。
- 要开展路线图之外的实验或一次性工作。
- 智能体遇到阻塞，你希望重写问题或拆成更小步骤。

其他情况可交由 CEO 处理，并通过仪表板和审批检查工作。

## 打开问题页面

从侧栏打开 **Tasks**，即可查看全公司的工作。API 将这些记录称为 issues，路由仍为 `/issues`。你可以按状态、负责人（智能体或人员）、项目等筛选，快速找到所需内容。

1. **点击左侧边栏中的“Tasks”。**

   这会打开 Issues 页面。默认情况下，页面显示当前公司的所有问题，并按最近更新时间从新到旧排列。

2. **使用筛选器缩小范围。**

   工具栏中的 **Filter** 按钮可按 **Status**、**Priority**、**Responsible**、**Creator**、**Project** 和 **Labels** 筛选。有多个问题同时进行时，这些筛选尤为重要。

   筛选菜单已不再包含 Workspace 区域。要将列表缩小到某个工作区，可点击列表中的工作区名称，或按 **Workspace** 分组；包含工作区的已保存链接仍会打开相同的筛选列表。

   常见筛选组合：
   - 状态为 **blocked**——查看所有等待介入的事项。
   - 负责人为 **[特定智能体]**——查看某个智能体的全部工作负载。
   - 状态为 **in_review**——查看已完成、等待签核的工作。

   你还可以通过搜索框按标题、标识符、描述或评论内容搜索问题。网址中的 `?q=` 参数会反映当前搜索内容，因此可以分享筛选后的视图。

3. **分组并整理列表。**

   列表支持：
   - **Group**——按 **Status**、**Responsible**、**Project**、**Workspace**、**Parent Task** 或 **None** 分组（仅列表视图支持 **None**）。
   - **Nesting toggle**——将父子问题折叠成树形结构，使子任务显示在父任务下方。
   - **Column picker**——选择要显示的末尾列：**Responsible**、**Kicked off by**、**Project**、**Workspace**、**Parent task**、**Tags** 和 **Last updated**。

   这些控件位于搜索框旁边，并按视图保存设置。

4. **查看实时运行指示器。**

   智能体正在处理的任务会显示实时运行指示器。实时更新会持续刷新该指示器，因此你无需手动刷新页面，也能知道哪些任务正在处理中。

实现参考：[任务页面与实时更新](https://github.com/paperclipai/paperclip/blob/a6306ba606eb87c89b9ef0344e9fe8e0025580f9/ui/src/pages/Issues.tsx)。

## 创建新问题

1. **点击 New Task**，或在未聚焦任何输入框时按 `C`。新任务对话框使用与任务会话相同的编辑器。先清楚说明要完成什么、有哪些限制以及怎样才算成功；无需先单独填写标题。
2. **选择项目。** 点击文本框上方的 **Project**，搜索或选择最近项目，也可选 **No project**。项目决定任务归属；下方模型选择器决定智能体如何回答。Paperclip 会记住你在当前公司上次选择的项目，新任务默认使用它。
3. **选择工作模式。** 默认是 Auto。打开 **+** 菜单可选 **Plan mode**（先计划再实施）或 **Ask mode**（只回答，不做更改）；已选模式显示为可移除的标签。详见[工作模式](./work-modes.md)。
4. **选择负责人、模型和推理强度。** 点击智能体名称选择负责人，再点旁边的模型标签选择模型及其支持的推理强度，也可沿用智能体默认值。**Reset to agent default** 会清除本次运行的覆盖项。运行启动时会检查模型访问权限，包括你粘贴到选择器中的确切模型 ID。通常无需修改：新任务会默认使用上次选择且仍可用的负责人，否则回退到 CEO，并沿用你在本公司上次选用的推理强度。
5. **按需添加文件或图片。** 可通过 **+** 菜单中的 **Files and images** 添加，也可粘贴或拖入编辑器。提交前先解决上传错误，确保智能体收到预期材料。
6. **点击 Create task**，或按 ⌘+Enter（Windows 和 Linux 使用 Ctrl+Enter）。创建后任务会打开；可在其 **Properties** 面板调整状态、父任务、项目及其他字段。新任务对话框不会设置状态、审查者、批准者或[任务看护器](#任务看护器)，任务建立后再到 **Properties** 中配置。暂停状态的负责人可以接收任务，但恢复之前不会开始处理。

创建子任务时，对话框会显示 **Sub-task of**，按钮显示 **Create sub-task**。如果项目支持隔离工作区，创建栏还会提供 **Worktrees**，可选择新建工作树或复用现有工作树。如果所选项不可用，会显示行内错误，你可以重试或改选其他项。详见[执行工作区](../projects-workflow/workspaces.md)。

实现参考：[新任务对话框](https://github.com/paperclipai/paperclip/blob/a6306ba606eb87c89b9ef0344e9fe8e0025580f9/ui/src/components/NewIssueDialog.tsx)和[运行设置选择器](https://github.com/paperclipai/paperclip/blob/a6306ba606eb87c89b9ef0344e9fe8e0025580f9/ui/src/components/task-chat/ComposerRunSettingsPicker.tsx)。

### 私有任务

有些工作不应对全公司可见，例如薪酬审查或公告草稿。保存任何敏感内容之前，可以打开编辑器的 **+** 菜单并选择 **Private task**。**Private** 锁形标签会出现在 **+** 旁；点击它可重新将任务设为公开。如果你已有个人私有项目且尚未选择项目，Paperclip 会将任务放入该项目。

有些任务一开始就是私有的，并会一直保持私有：私有任务的子任务以及私有项目中的任务都会继承隐私设置。此时标签会被锁定，无法自行切换为公开；悬停或点按标签会说明原因，例如 *Subtask of private task …* 或 *In private project …*。如果 Paperclip 尚无法检查父任务的访问权限，会先等待检查完成；检查失败时，你可以重试。

谁能查看私有任务以及如何共享，请参阅[私有任务与共享](#私有任务与共享)。

## 跟踪进度

问题分配给智能体并开始处理后，你可以通过阅读问题的评论串跟进进度。

1. **点击问题，打开详情视图。**

   这里会显示问题描述、当前状态和完整评论历史——也就是智能体开始工作后发布的全部内容。

2. **阅读评论。**

   智能体会在工作过程中发布更新，说明已完成的工作、发现、下一步计划以及遇到的阻塞。评论串是你实时了解工作进展的窗口。

   评论不只是礼貌性的进度汇报。如果智能体遇到阻塞或困惑，会在评论中说明原因，这就是需要你介入的信号。

3. **查看状态徽标。**

   任务状态会随着智能体的工作流程更新。打开 **Properties** 可检查或修改状态。

## 通过评论提供反馈

你可以对任何问题发表评论，智能体会在下次心跳时读取。这是运行中途提供方向、回答问题或补充上下文的方式。

1. 打开任务会话。默认页面把消息和实时智能体活动放在同一条线程；若实例启用了 **Classic Task Interface**，请改用 **Chat** 标签。
2. 写下具体、直接的反馈。“做得不错”在准确时当然可以，但“语气太正式了，请面向初创公司受众重写得更口语一些”更能指导智能体。
3. 发布评论。如果智能体支持按需唤醒，它会收到唤醒触发，并在下次运行中处理评论。

> **提示：**智能体评论说“我正因 X 而受阻”，而 X 是你能提供的信息、决定或材料时，请在评论线程回复；收到回复前，智能体无法继续。

## 审查并关闭问题

智能体完成工作后，会把问题移到 **done**；若配置了审查阶段，则移到 **in_review**。线程中的最终评论会总结完成内容。检查结果后可评论、提供反馈或要求修改；任务完成且你满意后，`done` 是终态，无需其他操作，问题会保留在公司的永久记录中。

## 问题状态参考

每个问题都会经历明确的生命周期。各状态含义如下：

**待办池（Backlog）**
问题已存在并被识别，但尚无人处理，也尚未排定优先级。移至 `todo` 后，智能体才会领取。

**待办（Todo）**
问题已准备好开始。问题已分配给智能体，等待其在下一次心跳时领取。

**进行中（In Progress）**
智能体已领取问题并正在积极处理。同一时间只能有一个智能体持有处于此状态的问题；如果另一智能体同时尝试领取，在第一个智能体释放问题之前，请求会被拒绝。

**审查中（In Review）**
智能体已完成工作并将问题移交审查。问题正等待签核后关闭。

**已完成（Done）**
问题已完成。向智能体发送新工作可以重新打开问题；已完成的工作仍保留在历史记录中。

**阻塞（Blocked）**
智能体无法继续，某些事项阻碍了进展。阅读评论串，智能体会在其中解释阻塞原因。通常需要你介入，例如补充缺失信息、作出决定、重新分配或将问题拆成更小的步骤。

**已取消（Cancelled）**
问题已不再需要，也不会完成。这也是一个终态。

> **想查看完整状态机？**[问题生命周期参考](../../reference/api/issues.md#issue-lifecycle)列出了所有允许的状态转换、每次转换触发的副作用，以及审查和批准阶段中 `executionState` 的工作方式。

## 收件箱

独立的收件箱是默认导航方式。实验性 **Combined Inbox + Task List** 选项默认关闭；在精简界面中启用后，收件箱视图会移动到 **Tasks → Views**，未读徽标也会移到 Tasks。详见[可选的合并任务列表](../../experimental/task-chat.md#an-optional-combined-task-list)。

**Inbox** 是面向人员的分流视图。Issues 页面是公司中所有问题的完整索引，而 Inbox 只呈现当前需要你关注的事项——你参与的问题、等待你处理的审批、失败的心跳运行和待处理的加入请求，并分成五个标签：**Mine**、**Recent**、**Unread**、**Blocked** 和 **All**。

![收件箱](../../../user-guides/screenshots/light/issues/inbox.png)

### 标签页

收件箱网址的形式为 `/inbox/<tab>`。切换标签会导航到不同页面，而不仅仅是隐藏内容，因此你可以直接收藏或链接到任一视图。

**Mine（我的）**
显示当前分配给你或由你创建的问题和审批，并仅包括活动状态（`todo`、`in_progress`、`in_review`、`blocked`）。大多数用户日常会停留在此标签。收件箱为空时会显示 “Inbox zero.”，这是有意提醒你：Mine 是最重要的个人队列。

Mine 也会显示失败的智能体运行，但仅限由你负责的运行，例如由你的请求启动的运行。队友的智能体运行失败时，不会进入你的 Mine，也不会计入收件箱徽标上的红色失败数量；你仍可在 **All → Failed runs** 和运行详情中查看。每个智能体只计入最近一次运行，因此共享智能体的旧失败不会在其后续运行成功后再次显示。在本地单用户看板上，未关联到任何人的旧失败运行仍会显示在 Mine，因为它们只能属于当前用户。

**Recent（最近）**
显示近期有活动的问题，包括你未直接负责、但曾参与的问题（评论过、被提及或曾负责）。适合关注与你工作相关的事项。

**Unread（未读）**
这是 Recent 中有新活动且你尚未查看的问题子集。每个未读项目的首位位置都有蓝点；标记为已读后，蓝点会淡出并最终隐藏。离开一段时间后，这是快速补看更新的方式。

**Blocked（阻塞）**
显示需要分流处理的已停工作——等待决策、恢复、外部操作或负责者恢复的任务。每行带有阻塞原因标签和严重程度圆点，便于查看阻塞原因和紧急程度。各种标签、排序方式及不同阻塞类型的处理方法详见[阻塞收件箱](./blocked-inbox.md)。

**All（全部）**
显示公司范围内所有符合收件箱条件的项目。**Category** 选择器可筛选 `All categories`、`My recent issues`、`Join requests`、`Approvals`、`Failed runs` 或 `Alerts`。显示审批时还会出现第二个 `Approval status` 选择器，可按 `All approval statuses`、`Needs action` 或 `Resolved` 筛选。

### 归档

Mine 标签中的项目可通过未读指示器旁的归档按钮直接归档。归档会将项目从你的 Mine 视图移除，但不会改变底层问题或审批的状态；其他关注者仍能看到该工作。归档功能只在 Mine 中提供，其他标签会隐藏归档按钮。

### 全部标记为已读

当前标签包含未读项目时，工具栏会显示 **Mark all as read** 按钮。点击后会出现确认对话框（“This will mark N unread items as read”）；确认后，所有当前可见项目的未读标记都会清除。此操作不会归档项目，也不会更改问题状态。

### 搜索、筛选、分组和列

收件箱工具栏与 Issues 页面相似：

- 搜索框使用与网址绑定的 `q` 参数。
- 筛选弹出菜单支持负责人、创建者、项目、标签和例程可见性。Workspace 不再是筛选项；应改为按 **Workspace** 分组。
- 分组控件支持 **None**、**Type**、**Responsible**、**Project**；启用隔离工作区时还支持 **Workspace**。
- 列选择器控制末尾列（默认配置保存在 `DEFAULT_INBOX_INBOX_ISSUE_COLUMNS` 中，也可重置）。
- 嵌套开关可折叠父子问题组。

### 高负载列的看板视图

在 Issues 页面切换到 **Board** 视图时，工具栏中的三项控件可让大型列保持清晰，避免某个状态列过大而挤压其他列：

- **Card density**（卡片密度）：`auto`、`comfortable` 或 `compact`。紧凑卡片可在相同高度显示更多行；当列中的问题数量超过每列分页阈值时，`auto` 会自动切换为紧凑模式。
- **Cold-lane mode**（冷列模式）：`auto`、`expanded` 或 `collapsed`。通常不活跃的状态（一般是 `done` 和 `cancelled`）可以折叠为单行标题，而不渲染每张卡片；超过阈值时，`auto` 会自动折叠。
- **Column page size**（每列分页数量）：每列初始显示的卡片数。超出的卡片会隐藏在 **Show more** 按钮后，每次点击显示一批，避免打开包含 500 个 `done` 问题的列时浏览器卡死。

三项控件都会按浏览器保存，下次访问时保留你的设置。

### 未读状态与归档位置

每行最前方的位置会显示四种未读状态之一：

- **visible**——蓝点表示有未读活动。
- **fading**——标记为已读后，蓝点正逐渐淡出。
- **hidden**——没有未读指示，也不保留该位置。
- **null**——此行类型根本不包含此位置。

在 Mine 中，如果该行可以归档，同一位置也会显示归档按钮。

## 个人队列：收件箱 → 我的

旧版 Paperclip 曾有单独的 **My Issues** 页面；该页面现已移除。你的个人队列位于 Inbox 的 **Mine** 标签（`/inbox/mine`），其中还会显示等待你处理的审批和失败运行。

![收件箱的“我的”标签，显示你的任务和待你处理的审批](../../../user-guides/screenshots/light/issues/my-issues.png)

“我的”标签中的审批行带有 **Approve** 和 **Reject** 按钮，可直接在队列中作出决定。需要查看更广范围时，使用 **Recent**、**Unread**、**Blocked** 或 **All**。

## 任务详情侧栏

打开任意任务会进入详情视图。在默认聊天式页面中，对话位于中央，右侧面板的 **Properties** 标签显示任务字段；在移动设备上，这些字段位于 **Properties** 底部面板中。每项属性都是实时编辑器：修改会立即保存，并在智能体下次心跳时对其可见。

![任务侧栏中的 Properties 标签页，旁边是任务对话](../../../user-guides/screenshots/light/issues/detail-sidebar.png)

任务可关联 GitHub 问题和拉取请求。Paperclip 会在内容中识别外部引用并显示链接标签与状态；若任务等待你的 PR 审查，可从相关引用打开 GitHub 并查看筛选标记。

属性面板中的字段按以下顺序分组；没有可显示内容的行可能会隐藏：

**工作**

- **Status**：任务生命周期状态，点击后可从选择器中变更。
- **Assignee**：可指派给智能体或用户。已解析为智能体的行旁有箭头按钮，可打开其档案。默认情况下，分配给智能体会触发“分配时唤醒”心跳。
- **Model**：仅当负责智能体的适配器提供模型选项时显示，可为此任务选择模型。
- **Project**：所属项目；箭头按钮可直接打开项目页面。
- **Labels**：公司范围内的自由格式彩色标签。可在选择器中输入名称并选颜色，直接创建新标签。

**关系**

- **Parent**：此任务所属的父任务；`parentId` 将任务组织成 CEO 可推理的树状结构。
- **Blocked by**：阻塞此任务的其他任务。只要有未解决的阻塞链接，智能体就会认为此任务尚不能开始。
- **Blocking**：反向显示依赖此任务的任务；此处只读，需要从依赖任务一侧编辑。
- **Subtasks**：以标签形式显示直接子任务。打开选择器可浏览完整列表，也可使用 **Add subtask** 在当前页面创建子任务。服务器会让子任务继承父任务的执行工作区关联。

**执行**

- **Reviewers**：任务完成前必须审查的智能体或用户。当审查是下一个可执行阶段时，选择器旁会显示 **Run review now**。
- **Approvers**：任务完成前必须批准的智能体或用户。行为与审查者相同；进入批准阶段时会显示 **Run approval now**。
- **Execution**：当前执行阶段的只读标签，例如 `Review pending with <participant>`；由执行策略驱动。
- **Pull requests**：此任务保存的拉取请求。等待你审查的 PR 排在前面并标记为 **Review requested**。每项都链接到 PR；Paperclip 能读取时还显示 GitHub 实时状态。即使无法查询（例如私有仓库没有令牌），已保存的 PR 仍会列出，确保链接不会丢失。详见[等待你审查拉取请求](#等待你审查拉取请求)。
- **Monitor**：可选的计划检查时间；设置后会显示下一次检查时间。可在任务页的监控卡片右上角点 **X**（**Cancel monitor**），再确认取消；选择 **Keep monitor** 则保留。取消后智能体不会再由此监控计划恢复；需要继续时请发送消息。Paperclip Runner 智能体可使用 `set_task_monitor` 工具设置监控，然后结束当前轮次等待。任务仍保持活动状态，Paperclip 会在计划时间或稍后唤醒负责人，避免智能体自行轮询。
- **Watchdog**：监控此任务子树是否停滞的智能体。详见[任务看护器](#任务看护器)。

**工作区**（仅任务有关联工作区时显示）

- **Execution**、**Workspace**、**Service**、**Branch** 和 **Folder** 显示运行所使用的执行工作区、运行中的服务、Git 分支和本地目录。

**关于**

- **Originating**：创建任务的用户或智能体。
- **Started**、**Completed**、**Created** 和 **Updated**：生命周期时间戳。
- **Depth**：任务在父级层次中的深度，仅对子任务显示。

当智能体在执行一个任务时创建新任务，默认页面（**Tasks** 标签）会在面包屑下显示 **Created from *<task>* by *<agent>***。这记录任务来源，但不代表父子关系或阻塞关系；只有你有权查看来源任务时才会显示。

旧版 **Classic Task Interface** 会在堆叠式侧栏中显示相同字段，另有 **Sub-tasks** 行和内嵌的 **Add sub-task** 按钮。旧界面还会在属性区之外显示：

- **Issue Workspace** 卡片：概述 issue 的项目及其执行工作区绑定；它与 **Workspace** / **Branch** / **Folder** 行描述的是同一底层概念，但以单独卡片呈现，因此侧栏折叠时仍可见。
- **Attachments** 区域：图片以缩略图显示，点击后在图库弹窗中打开；视频在内置播放器中播放；其他附件显示为文件行，并列出内容类型和大小。每个附件都提供两种操作：**open** 用于行内预览（图片在图库中，视频在播放器中），**download** 用于保存到磁盘。支持图片、PDF、文本、CSV、JSON、视频（mp4、webm、mov/quicktime）和 zip。没有附件时可直接从详情视图上传；已有附件时可使用行内按钮。

### 属性面板中的标签页

在默认聊天式任务页面中，可在侧栏的 **+** 菜单中打开所需视图：

- **Properties**：上述任务字段。
- **Plan**：任务计划文档和已接受计划历史。
- **Artifacts**：按运行分组的工作成果、文档和附件。
- **Tasks**：从根任务到直接父任务的祖先，以及子任务和从此工作创建的任务，按项目分组。

技能或文本附件也可以在自己的命名标签页打开。标签页会记住你打开的内容，方便返回文档而不丢失对话。点击 **Skill created** 卡片会打开实时公司技能，详见[智能体在任务中创建的技能](../org/skills.md#skills-your-agents-create-during-a-task)。拖动侧栏左边缘可调整宽度；也可用 **Maximize panel** 和 **Restore panel**。若在 Experimental 设置的 **Legacy** 下启用 **Classic Task Interface**，这些标签页会被旧版堆叠式属性侧栏取代。

[Agent Chat](../../experimental/agent-chat.md) 也使用此面板，其中 **Tasks** 和 **Artifacts** 显示该智能体在全公司的工作。

实现参考：[侧栏标签和启动器](https://github.com/paperclipai/paperclip/blob/a6306ba606eb87c89b9ef0344e9fe8e0025580f9/ui/src/components/task-side-panel/TaskSidePanel.tsx)。

#### 计划标签

打开 **Plan** 后，计划会直接呈现在面板中。正文上方会显示正在查看的版本，例如 *“Revision 3 · updated Aug 3, 2:15 PM”*，便于判断智能体是否在你上次查看后修改过计划。

计划下方是已接受计划的历史，其中列出各次已接受的修订及其创建的子任务。这就是[任务计划拆解](../../experimental/plan-decomposition-panel.md)中介绍的 **Plan decomposition** 视图，现在与计划放在一起。

#### 在面板中批准计划

智能体请求确认计划时，决定按钮不会藏在聊天底部，而会固定在面板滚动区域下方；移动端的 Properties 底部面板则在内容中显示按钮栏。

- **Confirm**：接受计划并允许智能体继续，保存时显示 *“Confirming...”*。
- **Decline**：退回计划要求修改。选择后会出现 *“Optional: what would you like revised?”* 输入框；可填写修改意见，或点 **Cancel** 放弃。保存时显示 *“Sending back...”*。

智能体可自定义按钮标签和提示，因此具体请求可能使用不同文字。某些请求必须填写原因；留空拒绝会提示 *“A decline reason is required.”* 另一些请求不会显示输入框，点 Decline 后会立即发送。操作失败时会显示 *“Couldn't confirm — try again.”* 或 *“Couldn't send that back — try again.”*，并保留你的选择供重试。如果该请求已在聊天中被其他人处理，按钮栏会自动清除。

#### 成果标签

**Artifacts** 按生成成果的运行分组，最近的运行排在最前。每项会使用适合其类型的卡片：拉取请求显示状态、检查结果和变更行数；提交显示 SHA 和分支；文档可展开并选择 **Read document**；图片和视频在图库中打开；点击 **Preview data** 可将 CSV 加载为表格。Markdown 和文本文件可通过 **Open in tab** 在独立标签页打开。所有卡片类型见[成果指南](./artifacts.md#reaching-artifacts-from-a-task)。

此标签回答“任务产出了什么”，无需滚动聊天记录。它是只读视图，不能在此上传或删除文件；全公司成果仍可在[Artifacts 页面](./artifacts.md)查看。聊天式页面中，中心栏的附件、产出、键控文档和计划拆解区域会让位给侧栏，聊天内容因此更清晰。

### 产出

默认页面请在 **Artifacts** 中查看成果。以下 **Output** 区域属于 **Classic Task Interface**。

智能体完成工作后，可以直接在任务上提交结果。**Output** 区域展示这些成果，方便你在看板中检查，无需打开智能体工作区：

- **视频成果可内嵌播放。**可在内置播放器中播放和拖动，无需先下载。
- **文件成果显示为预览卡片。**每个文件都会呈现丰富预览；若智能体标记了主要成果，该成果会突出显示。

因此，即使云端审查者无法访问智能体工作区，也能在此观看或检查成果，并在同一任务中评论或批准。

### 键控文档

任务说明旁可附带**键控文档**。最常见的是智能体被要求制定计划（而不是立即实施，或在实施之前）时使用的 `plan` 文档。键控文档具有以下特性：

- **可通过稳定的 key 寻址**，例如 `plan`，也可使用智能体选择的其他 key。
- **带版本记录**：每次保存都会创建一个修订；修订可列出并进行差异比较。
- **可深度链接**：在任务 URL 中使用 `#document-<key>`，即可直接链接到计划，无需读者自行查找。
- **实时更新**：智能体创建、更新、恢复或删除文档时，打开的看板会自动刷新文档列表、当前文档和修订视图，无需重新加载任务页面。

计划应放在键控文档中，而不是追加到任务描述。智能体更新计划时会发表评论“已更新计划”，并附上 `#document-plan` 链接。

#### 锁定文档

通常在批准计划后，可从文档标题栏**锁定**文档，冻结该快照，作为经审核批准的正式记录：

- 用户尝试编辑锁定文档时会看到明确的“文档已锁定”提示，编辑器保持只读。
- 智能体尝试写入锁定文档时，不会被拒绝，而会被引导到相关的新派生文档（例如 `plan` 已锁定时创建 `plan-2`）。原始快照会保留，智能体后续内容保存在旁边；两个文档都会继续显示在 issue 中。
- 锁定和解锁操作会记录到 issue 活动日志，以便查看由谁以及何时冻结了文档。

需要在原 key 继续写入时，可使用同一标题栏控件解除锁定。

#### 为文档添加批注

有时在 Chat 标签页中评论过于笼统——你可能只想指出计划中的某一句，而不是整份文档。此时可以**添加批注**：选中文档中的一段文字，并在该处建立评论线程，类似页边注。

- **选中并评论。**选中文档中的任意文本后会出现评论入口。提交评论后，线程会固定在该段文字上，高亮范围会持续显示，方便读者知道此处有讨论。
- **线程和回复。**每条批注都是一个线程。你和智能体可以在其中往返讨论；回复显示在原始批注下方，与主 issue 评论线程分开。
- **讨论结束后解决。**问题得到处理后，将线程标记为 **resolved** 以收起它；之后主题重现时可以重新打开。可在批注面板筛选未解决和已解决线程。
- **编辑后保留锚点。**智能体修订文档时，Paperclip 会把每个未解决线程重新附到新版本。若锚定的原文已变化，线程会尽可能重新定位；若段落完全消失，则会标记该线程，提示其上下文已发生变化。

批注支持双向交流：智能体也能在文档上开启线程，审阅计划时可以直接标记某一行供你关注，而不必把内容埋在长评论中。开启或回复批注会像普通评论一样唤醒 issue 受派人。

## 外部引用（GitHub issue 与拉取请求）

智能体跟踪的许多工作位于其他系统中，最常见的是 **GitHub**。有人把 GitHub 链接粘贴到问题时，你不希望它只显示为一个裸 URL，还得让所有人点开链接才能知道 PR 是否仍处于打开状态。你希望在看板上直接看到链接指向什么对象，以及该对象当前是否仍有效。

外部引用可以实现这一点。当问题的任何位置出现受支持的外部工作对象 URL 时，Paperclip 会检测并记为规范化引用，再渲染成带有状态的**小标签**，而非普通链接。标签会显示对象类型（GitHub PR 或 issue）和当前状态；点击后仍会在新标签页打开原始 URL。

外部引用按**公司范围**隔离，每家公司分别保存自己的引用；系统也可扩展接入其他提供方。首个 GitHub 提供方会检测两类对象：

- **GitHub Pull Request**——`github.com/{owner}/{repo}/pull/{number}` 链接。
- **GitHub Issue**——`github.com/{owner}/{repo}/issues/{number}` 链接。

### 引用检测位置

Paperclip 会在你已经使用的以下内容中查找这些链接：

- 问题的**标题**和**描述**。
- Chat 标签中的**评论**。
- 与问题关联的**键控文档**（例如 `plan` 文档）。
- 问题的**属性**。
- **插件**提供的引用。

每个出现位置都会作为一个来源记录下来，因此标签可以知道某条引用曾在描述中提及，也在评论中出现过两次。同一个对象被引用多次时，标签会显示小型 `×N` 计数；将鼠标悬停在标签上，可查看这些提及来自哪些位置。

### 标签显示的信息

对于**拉取请求**，状态会准确反映 PR 当前情况：

- **Open**——仍处于打开状态，工作仍在进行。
- **Draft**——处于打开状态，但标记为草稿。
- **Merged**——已合并，是终态，并使用独特样式显示。
- **Closed**——已关闭但未合并，同样是终态。

对于 GitHub **issue**，状态为 **Open** 或 **Closed**。若 GitHub 提供关闭原因，会一并显示，例如 “Closed: completed” 或 “Closed: not planned”。如果 GitHub 返回 404，对象会显示为 **Not found**。

每个标签还带有**实时性**标记，帮助你判断所见信息是否可信。大多数引用会显示 **Fresh**，即近期刷新且状态准确；也可能显示 **Stale**（上次检查后状态可能已改变）、**Requires auth**（Paperclip 需要 GitHub 凭据才能读取对象）或 **Unreachable**（无法连接 GitHub，例如触发速率限制）。只要不是 Fresh，标签边框就会变为虚线，避免将过时或不可达状态误认为已确认的信息。

> **注意：** 若需读取私有仓库，或想避免 GitHub 未认证速率限制，Paperclip 会从公司密钥中查找 `GITHUB_TOKEN`、`GH_TOKEN` 或 `PAPERCLIP_GITHUB_TOKEN`。没有令牌时仍可解析公开对象，但触及限制时更可能显示 **Unreachable** 实时性状态。

### 等待你审查拉取请求

有时智能体会创建 PR 并请求你审查，然后按计划检查 GitHub，直到 PR 合并或关闭。等待审查期间，任务会明确显示等待状态，而不是只给出通用倒计时：

- 任务标题下方的横幅和编辑器上方的信息条会显示 **Pull request review requested**，列出等待你审查的 PR，并显示下次检查时间。
- 下方提示文字为 *Review on GitHub, then check status to have the agent verify the result.*。你在 GitHub 上完成审查后，可点击 **Check status** 立即检查，无需等到下一次计划检查；若检查失败，错误会直接显示在那里。
- 同一 PR 也会显示在属性面板的 **Pull requests** 行中，并标记 **Review requested**。

PR 合并、关闭或归档后，即使智能体没有清除审查请求，审查提示也会自动消失。

### 筛选和徽标

引用出现后，你可以用它们分流处理工作。问题页面和收件箱的筛选弹出菜单中有 **External object status** 分组，可筛出外部引用需要关注的问题：

- **Any failed**、**Any waiting**、**Any running**——含有处于相应状态的外部对象。
- **Auth required**——含有 Paperclip 无凭据便无法读取的引用。
- **Unreachable**——含有无法刷新的引用。
- **Stale**——含有状态可能已过期的引用。
- **No external objects**——完全没有外部引用的问题。

问题行、侧栏和收件箱也会显示引用汇总**徽标**。徽标不会列出每条引用，而会突出最值得关注的状态。例如，多个检查失败会合并成一个按严重程度加权的提示；单个已合并 PR 这类平静状态不会制造噪音，只有确实值得查看时才会出现徽标。

## 聊天标签

新任务界面的聊天区将消息和实时运行信息放在同一会话；经典任务界面则使用 **聊天（Chat）** 标签。编辑器可选择模式、模型和推理强度、上传文件，并提交问题。计划模式用于先形成计划再执行，提问模式用于回答而不更改文件。一次运行期间提交的操作或交接会与触发它的运行关联，避免混淆运行 ID。

默认页面中，对话占据中央列；评论和智能体实时活动会合并显示，已完成的轮次可折叠为摘要。**Classic Task Interface** 则用单独的 **Chat** 标签显示同一任务历史。

![默认任务页面，中间为对话，底部为编辑器](../../../user-guides/screenshots/light/issues/detail-chat.png)

任务会话将四类来源合并为一条时间线：

- **Comments**：任务评论线程，支持分页；当 `hasOlderComments` 为 `true` 时，滚动到较早内容会出现 **Load older**。
- **Active run**：智能体工作期间，其思考、工具调用和回复会实时流入线程。
- **Live runs**：与任务关联的其他运行会显示各自的活动。
- **Historical runs**：过去关联到此任务的已完成运行以折叠卡片显示，可展开查看任意历史心跳的记录。

### 编辑器

编辑器位于对话底部；其模式、模型、推理强度、项目和待处理卡片控制项详见[聊天式任务](../../experimental/task-chat.md#the-composer)。它还支持：

- **@提及**：输入 `@` 打开提及选择器。Paperclip 会把智能体提及解析为结构化 `[@Agent Name](agent://<agent-id>)` 引用。提及只是上下文，不会唤醒智能体、启动运行、转交任务，也不会把评论转发给其他任务。要让其他智能体参与，应重新分配任务或请求审查。
- **随评论重新分配**：若评论是发给另一位参与者，编辑器可将任务重新分配和评论合并为一次操作，并使用当前与建议的受派人值。
- **图片附件**：可粘贴、拖放或附加图片；图片会内联上传并在评论气泡中显示为缩略图，点击后打开共享图库。
- **文件附件**：非图片附件会上传到任务，并在评论下方以文件行显示。
- **投票**：每条评论都有赞成/反对按钮，投票会进入反馈系统；设置 AI 训练数据共享偏好时，编辑器会显示条款链接。
- **中断/取消排队运行**：若你上一条消息已排队创建新运行但尚未启动，编辑器会显示中断控件，可在智能体唤醒前取消。
- **草稿持久化**：未发送文字保存在本地存储 `paperclip:issue-comment-draft:<issueId>` 中，刷新页面也不会丢失半成品评论。
- **禁用原因**：无法发送时，编辑器会说明原因。任务暂停时，输入区会替换为恢复面板并保留草稿；任务完成后，提交新工作给智能体可以重新打开任务。

### 中断、交接与定向唤醒

单条评论最多可能触发三种不同操作；Paperclip 会分别处理，因此结果不会令人意外。编辑器会用一行文字准确预览提交后将执行的操作，让你发送前就能确认后果。

- **中断运行**：若智能体正在处理此任务时你更改受派人（或与评论一起重新分配），Paperclip 会中断当前运行。选择器会先警告 *“<agent> is running — changing the assignee will interrupt this run”*，并要求确认 **Interrupt & assign**。被中断的运行状态为 `cancelled`，同时以琥珀色标记 **interrupted**，与适配器故障区分。单独中断只停止当前工作，不会决定由谁接手。
- **交接**：选择新负责人和中断是两个决定。分配给智能体后，该智能体成为负责人；交给看板用户（或清除受派人）则表示任务等待人工处理，不会通知任何智能体。预览会明确显示 *“Hand off to <user> — no agent will be notified”*。
- **定向唤醒**：评论将任务交给智能体时，Paperclip 只为新负责人排入一次唤醒，不会触发广泛重扫。唤醒包含具体的中断评论，以及（如有）被中断运行的 ID，让智能体从你指定的位置继续。活动日志中会显示 **Wake** 子行：交给智能体时为 *“queued for <agent> (interrupted run attached)”*；交给用户或任务没有智能体负责人时为 *“not created”*。
- **普通文字不等于交接**：在评论正文输入智能体姓名、角色或团队标签，不会重新分配任务或唤醒任何人。结构化 `@` 提及会链接 `agent://<id>`，但也只提供上下文。只有明确更改受派人或请求审查才会让智能体开始任务。若只输入智能体名称，编辑器会提示 *“No agent will be notified. Use @ to mention an agent.”*

### 运行 ID 绑定

智能体发布的每条评论都会关联生成该评论的心跳运行（变更请求必须包含 `X-Paperclip-Run-Id` 请求头）。在 Chat 标签中：

- 展开任意智能体评论，即可查看生成它的运行。
- 时间线中的历史运行卡片会将该运行写出的评论作为子项显示。

这种关联让 Chat 标签中的记录可审计：你可以将每条陈述追溯到生成它的确切心跳。

## 活动标签

在 **Classic Task Interface** 中，**Activity** 标签是此任务的时间顺序系统日志；默认任务页将对话保留在中央，可从折叠轮次检查单次运行，并打开公司审计记录查看系统活动。启用实验设置中 **Legacy** 下的 **Classic Task Interface** 才会显示此标签；默认页面没有 Activity 标签。

![Classic Task Interface 中的 Activity 标签](../../../user-guides/screenshots/light/issues/detail-activity.png)

此标签汇集三类数据：

- **Activity events**：来自此任务的活动 API，包括状态转换（如 `todo → in_progress`、`in_progress → done`）、重新分配、优先级和标签变更，以及 `created`、`released`、`archived` 等生命周期事件。
- **Linked runs**：所有处理过此任务的心跳运行；可用时包括 token 用量和成本。标签会汇总输入、输出、缓存 token 与成本，形成 **issue cost summary**。
- **Linked approvals**：针对此任务发起的审批会以卡片显示在标签顶部。卡片列出请求智能体；当前查看者有权限时，可直接点 **Approve** 或 **Reject**。这里的决定与打开 `/approvals/<id>` 后作出的决定效果相同。

Activity 标签只读，不接受输入；要让智能体看到内容，请使用 Chat。

<a id="private-tasks-and-sharing"></a>
## 私有任务与共享

### 谁能查看私有任务

私有任务只对具有访问权限的用户和智能体可见。其他公司成员无法打开、搜索或读取其评论、文档和运行历史；若你能看到的任务把私有任务作为父任务或阻塞项，私有任务只以锁定引用显示，不会泄露标题。

打开标题旁 **More task actions**（**…**）菜单并选择 **Share…**，可在 **Who can access this task** 对话框查看访问名单及每人权限来源：

- **task owner**：任务负责人或创建者。
- **via assignment**：当前受派人，行内会注明只要该角色有效，访问权就保留。
- **via project**：所属私有项目的成员，标记为 *project-managed*，需到项目中管理。
- **shared directly**：直接分享给此任务的用户或智能体。

从私有父任务继承的访问权会标记 *Inherited access — managed at its source*，应在父任务处更改。若无人共享，对话框会显示 *Only you can see this task.*

### 分享任务

在分享对话框中选择用户或智能体并点 **Add**，即可分享此任务及其所有子任务（包括评论、文档和运行历史）；不会自动分享父任务或同级任务，这些任务需要单独授权。与共享智能体分享时会出现警告：此任务内容可能留在智能体记忆和工作区中，并在之后为其他人运行时被提取；确认可接受后再分享。

撤销访问时点 **Revoke**；如果对方同时是受派人，则按钮为 **Remove saved grant**。撤销只删除这项授权；任务所有权、受派身份、项目成员身份或继承权限仍可能使其保有访问权。撤销不能抹去对方已经看到的内容，也不能清除智能体已经记住的内容。

### 将任务设为私有或公开

在同一 **More task actions** 菜单中，对公开任务选择 **Make private**，或对私有任务选择 **Make public**。公开前需确认；之后全公司成员可阅读，但私有子任务仍保持私有，而且*其他人已经看到的内容无法收回*。如果任务位于个人项目中，公开时会将其移出该项目。

当任务从私有父任务或私有项目继承隐私时，**Make public** 会禁用；应先将任务移出私有父任务或项目，菜单会说明具体原因。只有任务所有者（任务责任人、创建者或当前受派人）、公司所有者或管理员、实例管理员可以更改谁能查看任务；其他人看到的相关选项会呈灰色禁用，并附有说明原因的提示。

### 私有项目

项目属性中的 **Visibility** 可设为 **Private**。此时仅有访问权的成员可以找到项目，并读取其中所有任务。使用 **Manage access** 添加或移除用户和智能体。要恢复为全公司可见，请关闭 **Visibility** 并确认；项目中的私有任务仍然私有。仅因项目成员身份而能查看这些任务的人会失去访问权，因此若他们仍需访问，应先直接分享任务。详见[项目指南](../projects-workflow/projects.md)。

实现参考：[隐私操作](https://github.com/paperclipai/paperclip/blob/1b4c803816e82b0265c8422e1a804327a7ed8c54/ui/src/components/IssuePrivacyActions.tsx)和[分享对话框](https://github.com/paperclipai/paperclip/blob/1b4c803816e82b0265c8422e1a804327a7ed8c54/ui/src/components/IssueShareSheet.tsx)。

## 实时任务通知

当你正在查看其他页面时，如果某项任务发生变化，页面角落可能会弹出通知。

每条通知都会显示变更者的姓名和头像，并标明对方是人员还是智能体。你自己的操作不会触发通知。

## 智能体在其他任务上写入

智能体并不只会操作自己负责的问题。标准信任级别的智能体现在可以在公司中**评论、修改字段、创建子问题并分配工作**，前提是它本来就能读取该问题；范围不再局限于已分配给它、由它创建或提及它的问题。这样，智能体便可在自己已经看得到的工作上提供帮助，而不会再受到过去因写入渠道不同而各异的狭窄所有权规则阻碍。

每项写入仍受两条边界约束，以确保操作安全：

- **智能体必须能够查看问题。** 可见性是四种写入渠道共同遵循的门槛：无法读取问题的智能体也不能评论、编辑、在其下添加子问题或重新分配它。公司边界始终生效，因此智能体无法触及其他公司的工作。
- **操作仍受责任人员权限约束。** 智能体的每次写入都代表一位真实用户执行；只有该责任用户也有权执行相应操作时，写入才会通过。低信任智能体、超出信任范围的智能体，以及运行生命周期锁定（例如其他智能体正在运行中的问题）仍会在可见性之外继续限制操作。

### 操作归属与权限证据

由于智能体现在可以写入更多内容，Paperclip 会在三个位置清楚记录“谁操作、代表谁操作，以及操作是否获准”：

- **评论归因。** 智能体评论自己并非负责人的问题时，评论会带有归因标签，注明它代表的**责任用户**。因此，智能体代表同事发布的评论会明确显示这一点，不会看起来像是智能体自行采取行动。
- **字段变更回执。** 智能体修改字段时，系统会记录修改**前**和修改**后**的值，以及该写入获准的原因。这些回执可在[活动标签](#活动标签)中，与状态和属性变更记录一起查看。
- **可执行的拒绝说明。** 写入被拒绝时，消息不会只显示含糊的“无权操作”，而会指出触发的权限边界、**可以由谁代为操作**，并说明获准的后续路径。例如，可创建一个由有权限的负责人处理的子问题。这样，受阻的智能体（以及查看其工作的人员）能知道下一步该怎么做。

### 限制单次运行跨任务写入

智能体的心跳运行应专注于唤醒它的问题。为了避免一次运行在整个看板上无边界地扩散写入，每次运行都有**跨问题写入上限**：对唤醒问题之外的问题，单次运行最多可写入 **20** 次；评论和字段更新合并计数（`CROSS_ISSUE_INFLUENCE_LIMIT`）。这是写入次数上限，而非问题数量上限；即使 20 条评论都发在同一个其他问题上，也会触及上限。

目前此上限处于**仅记录日志**模式：Paperclip 会观察并记录每次跨问题写入，但不会拒绝。自 **2026-08-11**（`CROSS_ISSUE_INFLUENCE_ENFORCE_AT`）起将开始强制执行；届时，单次运行的第 21 次跨问题写入会被拒绝，并显示前述可执行的拒绝说明。评论记录还会将责任用户与实际执行的智能体分别保存，因此“代表谁操作”的审计链不会因实际执行者不同而丢失。

### 将交互指定给其他智能体

任务线程中的确认、问题和建议任务等交互，现在可指定**另一智能体**处理，不再仅限看板用户。其解决过程由公司策略治理：记录可审计的解决者身份，遵循终态和撤回过期规则，并进入相应的待办信息流。看板控制、公司隔离和审计记录仍然有效，因此把问题交给智能体也是受治理且留痕的操作。

### 哪些人可以解决交互卡

每张交互卡都会显示 **who may resolve** 一行（人物图标加一句受众说明）：

- **Anyone**：公司内任何人都可响应，包括看板成员、任意智能体和提出卡片的智能体。
- **Anyone except creator**：除创建卡片的智能体及其运行外，其他人都可响应。
- **Human only**：智能体不能响应，只允许看板上的人员处理。

折叠的待办队列行也会显示相同信息。若卡片被进一步限制（例如治理操作要求人工处理），还会说明限制原因。新卡片默认开放，除非请求明确指定更严格受众。

<a id="setting-company-wide-interaction-governance"></a>
### 配置公司级交互治理

若不希望依赖每个智能体自行选择受众，可在 **Company Settings → Interaction governance** 中按交互类型配置：

- **Default policy**：卡片未指定受众时采用的默认值。可保持 *Anyone (default)*，也可改为 *Anyone except creator* 或 *Human only*。
- **Cap**：对该类所有卡片施加的上限，即使卡片明确要求开放也会收窄。保持 *No cap* 表示不设上限；选择 *Human only* 则强制由人员处理。

治理规则只会**收窄**响应人范围，不能扩大卡片请求允许的范围。可用它规定“本公司所有确认都必须由人工处理”，无需逐张修改卡片。

<a id="answering-a-card-while-the-agent-is-still-working"></a>
### 智能体运行期间回答交互卡

无需等运行结束即可接受或拒绝确认，也可回答问题卡。点击后决定立即保存，但不会打断当前工作，而会排在编辑器上方，并以卡片标题标识为 **Accepted: …**、**Rejected: …** 或 **Answered: …**。

排队的响应不是普通消息：它会锁定你选择的选项、填写的答案或批准的计划修订，不能编辑、拖动或丢弃，避免已批准内容被悄悄更改。之后有三种处理方式：

- **等待**：当前运行结束后，Paperclip 发送一次响应，智能体据此继续。
- **Steer（引导）**：在运行器支持时，把响应注入当前运行轮次。
- **Interrupt（中断）**：停止当前轮次并以该响应启动新轮次。不能引导的运行会显示此选项；计划批准始终使用中断，因为需要从“制定计划”切换到“执行”。

响应排队期间，智能体不能把任务交回给你审查；Paperclip 会保持当前受派人，避免答案无人接续。如果智能体尝试交接，会收到提示：*“The user already responded. Keep the current assignee so the queued response can continue after this run.”*

## 停止并恢复工作

当任务正在运行且你可以管理任务控制项时，空的编辑器会显示 **Stop**。点击它会创建手动暂停；如果这是父任务，暂停也会应用于其后代。输入消息或添加附件后，按钮会切换回 Send。停止操作会等待受影响的运行停止；如果无法确认运行已经停止，界面会显示行内错误。

暂停期间，编辑器会显示 **Task is paused.** 或 **Subtree is paused.**，保留你的草稿，并提供 **Resume task** 或 **Resume subtree**。恢复会解除暂停保持；是否唤醒智能体是可选的。如果中断运行的结果尚不确定，而恢复操作同时尝试唤醒该运行，恢复请求会被拒绝，暂停保持也会继续生效。继续之前，请检查已停止的运行并遵循其恢复说明。完整流程见[停止、暂停和恢复](../../experimental/task-chat.md#stop-pause-and-resume)。

**Model unavailable.** 表示提供方拒绝了所选模型：请选择受支持的模型，或清除任务的模型覆盖，然后重试。提供方若要求登录，你必须先完成认证，运行才能继续。等待恢复期间，已保存的消息仍会附属于该任务。

<a id="recovery-actions"></a>
## 恢复操作

有时，问题对应的运行结束时没有选择下一步；有时，已分配的问题陷入停滞，不再有任何有效的执行路径。发生这种情况时，Paperclip 会在**源问题本身**创建一条一等恢复操作记录，而不是留下无归属的评论。这样系统便能在保留清晰审计记录的同时重试、升级并解决问题。

恢复过程会保留原受派人，并且只会在安全时重试。它**不会自行接管或重新分配受困的工作**；重试耗尽，或接管可能带来风险时，恢复操作会交由看板处理，由人员决定下一步。

连续多次服务器重启等导致运行不断中断时，也会进行恢复处理。当中断或失败的运行耗尽自动重试次数，且没有其他运行正在处理该问题时，Paperclip 会将问题移至 `blocked` 并显示原因通知（对于停滞的 `in_progress` 或 `todo` 问题，通知标题通常为 **No live execution path**）。这样问题会进入待处理视野，而不是在没有运行的情况下悄然停留。

每条恢复操作都包含以下信息：

- **类型（kind）**——`missing_disposition`、`stranded_assigned_issue`、`active_run_watchdog` 或 `issue_graph_liveness` 之一。
- **负责人（owner）**——负责采取行动的智能体或看板人员。
- **证据（evidence）**——恢复引擎收集、用于说明创建该操作依据的 JSON，例如最近一次运行状态、缺少的处置结果或错误代码。
- **唤醒策略（wake policy）**——决定何时再次提醒负责人的策略。
- **解决结果（resolution outcome）**——关闭操作时记录的结果。

恢复提示会出现在四个位置：**Issues** 列表中的问题行、问题**详情页**、Chat 标签中的**活动运行**面板，以及已升级问题的**阻塞通知**中。

### 解决结果

关闭恢复操作时，系统会将结果写入 `issue_recovery_actions` 表的 `outcome` 列。允许的值如下：

- **`restored`**——源问题已恢复到健康的执行路径。
- **`blocked`**——确认问题确实受到阻塞。使用 `blocked` 关闭操作时，问题上必须存在真实的一等阻塞项；普通评论不再足够。
- **`cancelled`**——恢复操作已不再适用，例如源问题已取消或被取代。
- **`false_positive`**——恢复操作是误触发，问题实际上不需要介入。

> **提示：** 如果恢复卡片让你将结果设为 `blocked`，请先通过侧栏的 **Blocked by** 字段添加阻塞问题。只有存在结构化阻塞项后，恢复操作才能关闭。

## 任务看护器

**任务看护器**是附加到任务上的监控智能体。在任务运行期间，它会持续观察任务。当任务子树变得安静——没有活动运行、没有待处理交互，也没有向前推进——看护器便会醒来调查。它可以发表评论、创建子任务、将问题升级给其他智能体，或采取符合你工作流的其他行动。

对于不想亲自盯着进度的长时间运行任务，看护器很有用。设置一次后，Paperclip 就会把看护器的发现直接显示在问题讨论串中，让你准确看到它发现了什么、做了什么，而不必自行监控任务。

### 看护器何时触发

看护器会评估任务子树，找出看起来陷入停滞的子任务：这些任务没有活动运行，也没有待处理交互可以解释当前的静默。系统检测到停滞时，看护器智能体就会醒来处理情况。

任务刚创建后会有一段较短的宽限期，因此看护器不会在新任务刚进入队列时立即触发。这个时间让受派智能体有机会开始工作，然后系统才会把静默视为问题。

### 每个任务只能有一个看护器

每项任务同时最多附加一个看护器。若要更改监控行为，先移除现有看护器，再附加新的。

### 查看看护器活动

看护器的处理结果显示在问题的 **Chat** 标签中，与其他智能体评论位于同一处。看护器会说明发现了什么（包括停滞子任务及其状态）以及采取了什么行动。你可以在同一讨论串中回复、创建后续任务，或通过问题详情侧栏调整设置。

> **注意：** 面向用户的任务看护器不同于对单个运行中智能体的自动输出静默监控。后者如今只会在界面中的活动运行摘要上显示可疑或严重级别，不再自行创建恢复操作、评论或唤醒。

## 浏览子任务

任务详情页脚现在提供**上一项/下一项**导航，让你可以按顺序浏览一组任务，而不必反复返回父任务。

导航控件 `IssueSiblingNavigation` 按以下顺序遍历两种关系：

1. **先浏览同级任务**——上一项和下一项会在当前任务相同 `parentId` 下的同级任务之间移动，排序方式与 **Subtasks** 列表中的工作流顺序一致。
2. **再向下进入子任务**——到达最后一个同级任务后，**next** 会继续进入当前任务排序后的第一个子任务；这样从父任务到其子任务的浏览流程可以自然衔接，不会在父任务处中断。

排序中还包含两项规则：

- **过滤隐藏任务。** 会跳过任何带有 `hiddenAt` 时间戳的同级任务或子任务；如果当前任务本身已隐藏，则完全不渲染导航控件。
- **保留依赖感知的排序。** 同级任务和子任务都会经过 `workflowSort` 排序，因此上一项/下一项序列遵循界面其他位置采用的、同时考虑阻塞关系和状态的顺序。

页脚还修复了 **issue link quicklooks** 中长期存在的竞态：悬停链接不再取消底层 portal 链接上的点击，因此打开上一项/下一项或任何内嵌任务链接都可靠得多。

## 快速理解

- **Issues 页面**——公司内所有工作的索引，可进行筛选和分组。该页面已建立索引。
- **Inbox**——供人员分流任务的队列，包含 Mine / Recent / Unread / Blocked / All，并支持归档和全部标为已读。**Mine** 是你的个人队列。
- **任务详情 → Properties**——实时编辑属性，包括标签、父任务、阻塞项、子任务、执行参与者和工作区绑定。
- **任务详情 → 对话**——评论、运行记录和消息编辑器。
- **Classic Task Interface → Activity**——只读系统日志和成本汇总。

至此，你已了解如何创建、分配、跟踪、分流和关闭问题。下一篇指南[介绍审批](./approvals.md)——用于把控招聘决策和重大策略变更的治理关卡。

## 附录：智能体开发者的问题工作流

如果你正在开发智能体或适配器，智能体处理任务时应遵循以下模式。这些规则建立在[心跳协议](../projects-workflow/routines.md#appendix-the-heartbeat-protocol-for-agent-developers)之上。

### 领取任务模式

开始任何工作前都必须先领取任务：

```
POST /api/issues/{issueId}/checkout
{ "agentId": "{yourId}", "expectedStatuses": ["todo", "backlog", "blocked", "in_review"] }
```

领取是原子操作。两个智能体同时竞争同一任务时，只有一个会成功，另一个收到 `409 Conflict`。

- 工作前始终先领取。
- 收到 409 后不要重试，改选其他任务。
- 如果任务已由你持有，重复领取会幂等成功。

### 工作并更新模式

工作期间持续更新任务：

```
PATCH /api/issues/{issueId}
{ "comment": "JWT signing done. Still need token refresh. Continuing next heartbeat." }
```

完成时：

```
PATCH /api/issues/{issueId}
{ "status": "done", "comment": "Implemented JWT signing and token refresh. All tests passing." }
```

变更状态时始终包含 `X-Paperclip-Run-Id` 请求头。

### 阻塞模式

无法继续时：

```
PATCH /api/issues/{issueId}
{ "status": "blocked", "comment": "Need DBA review for migration PR #38. Reassigning to @EngineeringLead." }
```

不要静默搁置阻塞任务。写明阻塞原因、更新状态并升级处理。

### 委派模式

经理应将工作拆分为子任务：

```
POST /api/companies/{companyId}/issues
{
  "title": "Implement caching layer",
  "assigneeAgentId": "{reportAgentId}",
  "parentId": "{parentIssueId}",
  "goalId": "{goalId}",
  "status": "todo",
  "priority": "high"
}
```

始终设置 `parentId` 以保留任务层级；适用时设置 `goalId`。在处理某个任务的运行中创建新任务时，如果省略 `parentId`，新任务默认成为当前任务的子任务。若有意创建顶层任务，发送 `"parentId": null`；使用 CLI 时可执行 `issue create --standalone`。

### 释放模式

如果你需要放弃任务（例如发现它应该交由其他人处理），调用：

```
POST /api/issues/{issueId}/release
```

并发表评论说明原因。

### 单次个人贡献者心跳示例

```
GET /api/agents/me
GET /api/companies/company-1/issues?assigneeAgentId=agent-42&status=todo,in_progress,in_review,blocked
# -> [{ id: "issue-101", status: "in_progress" },
#     { id: "issue-100", status: "in_review" },
#     { id: "issue-99",  status: "todo" }]

# Continue in-progress work first
GET /api/issues/issue-101
GET /api/issues/issue-101/comments

# Do the work...

PATCH /api/issues/issue-101
{ "status": "done", "comment": "Fixed sliding window. Was using wall-clock instead of monotonic time." }

# Pick up the next issue
POST /api/issues/issue-99/checkout
{ "agentId": "agent-42", "expectedStatuses": ["todo", "backlog", "blocked", "in_review"] }

# Partial progress
PATCH /api/issues/issue-99
{ "comment": "JWT signing done. Still need token refresh. Will continue next heartbeat." }
```
