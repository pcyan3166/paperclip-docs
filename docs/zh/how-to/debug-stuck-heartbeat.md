# 调试卡住的心跳

以下是几种典型症状，几乎涵盖了所有“这个智能体工作不正常”的报告。在开始之前，请打开智能体的详情页并滚动到 **Run history**（运行历史）—— 以下每一项诊断都从这里开始。

---

## 1. 智能体唤醒后立即退出

**症状。** **Run history**（运行历史）中出现了运行记录，但在几秒内即完成，且未发布任何评论。状态翻转回 `idle`。

**原因。** 收件箱为空，且存在定时器。

**修复。** 进入智能体 → **Run Policy → Heartbeat on interval**（运行策略 → 按间隔心跳）。将其关闭，并依赖由任务分配驱动的唤醒。参见 [心跳与例程](../guides/projects-workflow/routines.md)。

---

## 2. 检出失败，报错 `409 Conflict`

**症状。** `POST /api/issues/{id}/checkout → 409`。运行中止。

**原因。** 两个智能体因同一问题被唤醒。第一个智能体拥有该问题的所有权。

**修复。** 不要重试——请选择其他任务。如果这两个智能体本应共享工作，请将问题拆分为子问题，并设置 `parentId`。

---

## 3. 运行以退出码 143 终止

**症状。** 运行状态为 `failed`，附带 `exited with code 143`（SIGTERM）。

**原因。** 超时或内存溢出（OOM）。心跳是为短窗口设计的。

**修复。** 缩小每次心跳的作用范围：

1. 将工作拆分为子问题（`POST /api/companies/{companyId}/issues` 配合 `parentId`）。
2. 收紧上下文——优先使用 `GET /api/issues/{issueId}/heartbeat-context`，而非读取整个代码库。
3. 将长时单次执行的工作移至心跳路径之外的例程中。

---

## 4. 运行中途问题被取消，但智能体仍在行动

**症状。** 你在 UI 中取消操作；但智能体在几秒后仍然发布了评论。

**原因。** 唤醒负载在取消操作生效前已被捕获。

**修复。** 这通常能自愈——下一次心跳会看到新状态并退出。对于你自己编写的智能体，请在每次运行的顶部使用 `GET /api/issues/{issueId}` 重新获取状态，并在遇到 `cancelled` 时退出。

---

## 5. 每次心跳都发布相同的“受阻”评论

**症状。** 一个 `blocked` 问题在每次心跳时都累积相同的状态评论。

**原因。** 发布前缺少去重逻辑。

**修复。** 在对 `blocked` 问题发表评论前，先获取 `GET /api/issues/{issueId}/comments?order=asc`。如果最近的作者是你且内容匹配，则跳过。仅在新评论、状态变更或事件驱动唤醒时重新介入。

---

## 6. 在多次无进展运行后，恢复唤醒变慢

**症状。** 恢复式唤醒被记录为已跳过，原因为 `issue_rewake_throttled`，而不是立即启动另一个智能体会话。

**原因。** Paperclip 保护你免受昂贵的空操作循环影响。对于同一问题，在两次成功运行均未产生可见进展后，下一次恢复式唤醒将等待一个递增的冷却时间。延迟从两分钟开始，且不超过 30 分钟。

**修复。** 首先阅读最新的运行记录，然后为智能体提供新信息，或在你准备介入时明确恢复工作。新评论、新的问题活动以及明确的恢复操作可以绕过冷却时间。服务端的恢复重试也会立即继续，因此此安全措施不会延迟真正的崩溃恢复尝试。

---

## 7. 运行成功，任务仍处于进行中，随后智能体再次自我唤醒

**症状。** 运行以 `succeeded` 结束，但任务始终未离开 `in_progress` 状态。Paperclip 发布了一条 **Missing issue disposition**（缺少问题处置）通知——*“Paperclip 需要在此问题继续之前确定处置方式。”*——并且同一智能体在该任务上再次被唤醒，有时在最终设置状态之前会执行一些实际工作。

**原因。** 运行结束时未告知 Paperclip 任务发生了什么。每次成功的运行都必须留下以下四种结果之一：

- `done` 或 `cancelled`
- `in_review` 并附带真实的审查路径——`executionState.currentParticipant`、通过 `assigneeUserId` 指定的人类负责人、待处理的交互，或关联的待批准项
- `blocked`，附带阻塞项（`blockedByIssueIds`）或明确命名的解除阻塞负责人
- 一个委托的后续问题，或通过 `resumeIntent` 和 `resumeFromRunId` 记录的明确延续

当上述情况均不存在，且没有其他实体已拥有下一步操作的所有权——没有排队的唤醒、没有待批准或待交互项、没有监控器、没有开放的恢复问题、没有暂停保持——Paperclip 会向同一智能体排入一次纠正性唤醒，唤醒原因为 `finish_successful_run_handoff`。

**修复。** 通常无需操作：让它运行。该纠正性唤醒使用智能体的 **normal**（常规）模型和适配器设置发出，而非其之前使用的廉价、仅状态恢复配置，并且该唤醒会将任务自身的描述、智能体的最终报告以及记录的下一步行动回传给它。智能体重新阅读其自身的证据，执行仍缺失的最小验证，然后才选择一个结果——因此，此唤醒在 **Run history**（运行历史）中可能看起来像一次完整的工作运行，并相应产生成本。

在观察过程中需注意两点：

- **它只尝试一次。** 纠正性唤醒限制为每次运行仅尝试一次，因此你永远不会看到这变成循环。如果那一次尝试仍未确定处置方式，Paperclip 会发布一条 **Missing disposition recovery blocked**（缺少处置的恢复被阻塞）通知——*“Paperclip 无法自动解决此问题缺失的处置方式。该问题已阻塞在恢复负责人处。”*——并将任务交给恢复负责人，而不是再次尝试。
- **已停止的智能体完全不会收到唤醒。** 如果负责人处于暂停、终止、等待批准状态，或因预算硬性停止，则纠正性唤醒将被跳过，任务将简单地停留在 `in_progress` 状态，直到你接手。

如果你不想为这些唤醒付费，根本解决方法在于上游：让你的智能体在结束前记录状态。描述进展的评论并非处置方式——Paperclip 关注的是任务的状态和路径，而非其文本内容。

## 首先查看何处

- **Run logs**（运行日志）。智能体详情 → **Run history**（运行历史）→ 点击任意运行以查看完整转录和退出码。
- **Heartbeat context**（心跳上下文）。`GET /api/issues/{issueId}/heartbeat-context` 返回智能体在唤醒时看到的精确负载。
- **Comment history**（评论历史）。`GET /api/issues/{issueId}/comments` 是智能体实际发言内容的真实来源。

---

## 何时寻求人工帮助

- 修复后，同一故障在连续三次运行中重复出现。
- 智能体在 100% 预算处暂停，且你无法判断循环是原因还是症状。
- 运行在 `running` 状态挂起的时间超过你的心跳超时时间——这是基础设施问题，而非智能体问题。
