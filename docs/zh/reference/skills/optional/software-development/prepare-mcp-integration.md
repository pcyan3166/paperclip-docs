# 准备 MCP 集成

> 从输入链接或简报出发，完成新的 MCP 或供应商集成：先开展带引用的研究，中间设置明确的人工审批关卡，最后针对每个获批连接交付一个受治理的 Paperclip 连接器。

这是一个两阶段操作指南，用于研究并交付 MCP/供应商集成，确保过程可供审核和签核。它会将链接或简短供应商说明转化为带引用的研究拉取请求，等待人工接受确切修订版本，然后才编写连接器代码——每个获批连接对应一个 Paperclip 拉取请求。

此技能是**可选**目录技能，可按需安装。如何安装、审计、更新、分配和重置目录技能，请参阅[技能参考](../../../skills.md#3-app-shipped-catalog)。

## 适用场景

- 你正在研究新的 MCP 服务器或供应商集成，希望先将带来源的研究结果整理出来，再决定是否开发。
- 工程师、产品经理或研究人员需要留下完整记录——连接器会做什么、涵盖哪些连接，以及由谁批准——然后才提交代码。
- 你希望新的连接器工作遵循操作指南和审批关卡，而不是临时拼凑。

### 不适用场景

- 你正在编写临时连接器代码，并有意绕过操作指南；此技能的目的正是防止这种情况。
- 目前还没有要研究或交付的集成，只是对某家供应商有开放式问题。

## 两阶段流程

此技能严格区分研究和实现，并在两者之间要求人工决策。

### 阶段 A——研究（不实现）

阶段 A 从输入链接或供应商简报出发，在 `paperclip-content` 仓库中生成可审核且附有引用的**研究拉取请求**。它会收集集成所涉及的信息并附上来源，供人员阅读后决定是否继续。此阶段不会编写连接器代码。

### 人工审批关卡

阶段 B 不会自动开始。必须由人员明确批准**确切的研究修订版本**（通过唯一一个拉取请求的 head SHA 锁定），并指定要构建的连接集合。批准某个修订版本并不代表后续修订也获批；研究内容一旦更改，就必须重新审批。

### 阶段 B——实现

只有获得批准后，此技能才会在 Paperclip 应用中实现连接器。每个获批连接都会单独建立一个 Paperclip 应用拉取请求，因此每项连接都能分别审核和交付。

## 每个连接一个 PR 的规则

每个获批连接都要建立独立的 Paperclip 应用拉取请求，不得将多个连接捆绑在一起。这样每项工作都能单独审核，并明确记录每个连接获批和交付的内容。

## 密钥规则

供应商凭据必须始终存放在获批的密钥存储中，不得存放在其他地方。凭据不得出现在简报、目录文件、任务文本、计划、日志、分支名称、提交或拉取请求中。如果需要凭据，应引用密钥存储中的条目，不要将凭据粘贴到此技能生成的任何工件中。
