# 隔离工作区

默认情况下，项目中的每次任务执行都会在项目的主检出目录中工作，也就是所有执行共享同一个工作树。**Isolated workspaces**（隔离工作区）会为每次任务执行提供独立检出目录：在自己的分支上创建 Git 工作树，使多个智能体可以同时处理同一项目，而不会互相改动对方的文件。

![工作区页面](../../user-guides/screenshots/light/workspaces/list.png)

## 此功能的用途

共享检出目录会形成瓶颈，也有风险：两个并行执行如果编辑同一目录树，就会破坏彼此的工作；未完成的实验也会一直留在主检出目录中，直到有人清理。隔离工作区使并发执行更安全——每次执行都获得自己的分支、文件夹和运行时上下文，并根据策略创建和清理。

## 启用此功能

1. 前往 **Settings → Experimental**（设置 → 实验性功能）。
2. 开启 **Enable Isolated Workspaces**（启用隔离工作区），说明文字为：*“在项目配置中显示执行工作区控件，并允许新的和现有任务执行使用隔离工作区。”*

这是控制所有工作区界面的唯一开关：它控制侧边栏的 **Workspaces** 项目、每个项目的 **Execution Workspaces**（执行工作区）配置、新旧任务的工作区模式选择器，以及项目的 **Workspaces** 标签页。

> **注意：** 与大多数实验性标记不同，此设置在运行时也会强制执行。关闭此标记后，按任务设置的工作区会被忽略，执行会留在主检出目录中——关闭它相当于真正的紧急停止开关，而不仅仅是隐藏界面。

## 使用方法

仅开启实例级标记并不会自动隔离工作区——每个项目还必须自行选择启用：

1. 打开项目的**配置**，找到 **Execution Workspaces**。
2. 开启 **Enable isolated task checkouts**（启用隔离任务检出），说明文字为：*“允许任务在项目主检出目录和隔离执行工作区之间选择。”*
3. 可选：开启 **New tasks default to isolated checkout**（新任务默认使用隔离检出），然后打开 **Show advanced checkout settings**（显示高级检出设置），配置 Git 详细信息：基准引用（`origin/main`）、分支模板（`{{issue.identifier}}-{{slug}}`）、工作树父目录（`.paperclip/worktrees`）以及创建和清理命令。
4. 此后，新任务对话框（以及每项任务的工作区卡片）都会提供模式选项：使用共享检出目录、创建**新的隔离工作区**，或重用现有工作区。
5. 在侧边栏的 **Workspaces** 页面或项目的 **Workspaces** 标签页中查看活动工作区。每个工作区都有详情页，其中包含其任务、运行时服务和日志。

工作区详情页面（包括标签页、运行时控件和日志）的完整介绍，请参阅[工作区指南](../guides/projects-workflow/workspaces.md)。

### 两次执行都要使用共享检出目录时

隔离工作区通过为每次执行分配独立目录来解决并发冲突。不过，仍使用项目**共享**检出目录的执行依然可能互相冲突——两个智能体同时编辑同一个工作副本会破坏彼此的工作。**Execution Workspaces** 中的 **Shared workspace concurrency**（共享工作区并发）控件决定如何处理这种情况：

- **Auto**（自动，*默认值*）——在本地/SSH 运行器上进行并行执行；在 Cloud 沙盒中则轮流执行。Paperclip 会根据执行实际运行的位置选择安全行为。
- **Serialize**（串行）——在共享项目工作区中始终依次运行。无论运行位置在哪里，第二次执行都会等待第一次执行释放检出目录。
- **Allow**（允许）——执行不会因等待工作区而暂停；因此可能出现并发修改。只有在确定执行之间不会互相干扰时才应选择此项。

此设置属于项目策略；如果项目允许按任务覆盖，单项任务也可以指定自己的模式。未设置时，执行会解析为 **Auto**。

## 在环境中执行任务时

如果任务还会在某个[环境](environments.md)中运行（例如 SSH 计算机或服务提供商沙盒），还需要确定智能体实际编辑的是哪个文件系统。Paperclip 会将其记录为此次执行的*工作区实现方式*，分为两种模式。

在 `copy` 模式（常见模式）下，隔离工作区会复制到环境中，智能体在该副本上工作，执行结束时结果会复制回来。

在 `in_place` 模式下不会复制任何内容。环境中已经有权威文件和正确的工具链，因此执行会直接在环境自己的目录树中工作，路径即 Paperclip 所称的 `authoritativeRoot`，完成后也无需同步回传。本地工作树和分支仍然存在，只是此次执行不会对它们进行编辑。

你不需要选择此模式。环境的驱动程序或沙盒服务提供商会声明模式，Paperclip 会据此执行；项目和任务配置中没有相应设置。对于 Codex 执行，可以通过两个位置判断当前模式：在原位模式下，运行日志会显示 `[paperclip] Syncing CODEX_HOME to …`，而不是 `[paperclip] Syncing workspace and CODEX_HOME to …`；智能体进程还会收到 `PAPERCLIP_WORKSPACE_REALIZATION_MODE` 和 `PAPERCLIP_WORKSPACE_AUTHORITATIVE_ROOT` 环境变量，供你自己的脚本检查。

### 现在，工作区外的写入会明确报错

即使你从不使用环境，也应该了解这一点，因为它会改变执行出错时的表现。

在 `copy` 模式下，限制在工作区内的智能体沙盒只能获得同步目录树内的可写路径，或者由环境映射回该目录树的路径。如果传入的可写路径两者都不符合，执行会在智能体启动前停止，并显示指出该路径的错误：

> 可写沙盒路径 “…” 位于同步工作区 “…” 之外，且没有对应的回传映射。

这种失败正是预期行为。以前，执行期间此类路径仍可写，但工作区复制回来时更改会被悄悄丢弃；于是智能体可能完成任务、验证自己的工作并报告成功，而修改过的文件却无人可见。现在在启动时就报错，更便于处理：将路径移入工作区，或将其设为只读。

环境声明为别名的绝对路径（例如实际代表“工作区”的 `/app`）会自动绑定到同步目录树；如果它们指向其他位置，也会以同样明确的方式被拒绝。

## 关闭此功能时

侧边栏的 Workspaces 项目会消失（访问 `/workspaces` 会重定向到你的任务列表），项目和任务工作区控件会隐藏；并且由于上述运行时强制规则，所有执行都会在主检出目录中运行，即使任务之前配置了隔离设置也是如此。项目策略和按任务设置会保留在数据库中，重新启用后会恢复。

## 注意事项

- 要实现隔离，必须同时启用**实例级标记**和项目的 **Enable isolated task checkouts** 策略。
- 目前只有 Git 工作树这一种实现方式——界面会标注 *“由主机管理的实现：Git worktree。”*
- 同一区域中的高级 **Environment** 下拉菜单需要启用 [Environments](environments.md) 标记，并且至少有两个可选环境。
- 工作区范围的沙盒隔离（包括上述可写路径检查）仅在 Linux 主机上运行。
- 固定使用 ACP 引擎的 Codex 智能体无法在原位环境中运行：*“原位工作区实现需要 Codex CLI 引擎；不支持 ACP 归档暂存。”* 请将引擎留空，由 Paperclip 自动选择 CLI。
